# T-109 — SES bounce and complaint events to SNS: see mail failures, suppress in-app
Model: sonnet
Engine: claude

**Lane:** infra
**Context:** standard
**Touches:** infra/cdk/lib/compute.ts (SES configuration set, SNS topic, event destination), apps/api email-login (event consumer, in-app suppression check in the SES sender), admin console (email health counts, if cheap), config per environment
**Needs:** nothing open. The SES identities already exist via CDK (custom MAIL FROM, SPF/DKIM). Filed 2026-11-09 after the SES production-access review for live exposed the gap: today the only bounce/complaint protection is SES account-level suppression plus manual console checks — the platform itself never learns that an address bounced or complained.

## Why

Two reasons, in order:

1. **Deliverability hygiene.** SES account-level suppression stops repeat sends, but the application has no record of it. An invited counterparty whose address hard-bounces looks identical to one who simply has not responded — the deal team cannot tell "never received it" from "ignoring us."
2. **Our own words.** The SES production-access correspondence for live (Nov 2026) describes our bounce/complaint handling to AWS. Suppression + console monitoring is what we could truthfully claim. This task makes the stronger, standard setup real: events wired to SNS and into the app.

## Work

1. **Configuration set per environment** (CDK, alongside the existing EmailIdentity in compute.ts): an SES configuration set with an SNS event destination for BOUNCE, COMPLAINT, DELIVERY, REJECT and RENDERING_FAILURE events. All sends from the identity use this configuration set (set it as the identity's default configuration set, or pass the name on every send — pick one, apply it everywhere, test it).
2. **Consumer:** an SNS subscription feeding a small consumer (Lambda, or an API endpoint if the shape fits better) that validates the SNS signature, parses the SES event, and records it: event type, recipient, message id, environment, timestamp, diagnostic detail for bounces.
3. **In-app suppression:** a hard bounce or a complaint marks the address do-not-send in our own data. `SesEmailSender` checks the flag before sending and refuses with a clear logged reason. This sits on top of SES account-level suppression, never replaces it: SES keeps doing its job even if our consumer is down.
4. **Operator visibility:** structured logs for every event, plus bounce/complaint counts visible to platform operators (the admin console gains an email-health line if it drops in cheaply; otherwise a documented log query is acceptable for v1). No customer-facing surface.
5. **All environments:** dev, qa, stage and live identities each get the configuration set + topic via CDK config. No console hand-work.

## Guardrails

- The consumer must never break sending: if event processing fails, sends continue exactly as today (SES suppression is the floor).
- Record only what the events carry; no email body content is involved or stored. Payloads from SNS are signature-validated before parsing.
- Sandbox-safe: this must be testable while an environment is still in the SES sandbox, using the SES mailbox simulator.

## Acceptance

- In dev, sends to the SES mailbox simulator produce the full loop: `success@simulator.amazonses.com` records a delivery; `bounce@simulator.amazonses.com` records a bounce and lands the address on the in-app do-not-send list; `complaint@simulator.amazonses.com` does the same via a complaint event.
- A subsequent sign-in-code send to a suppressed address is refused before calling SES, with the suppression visible in logs.
- Existing email-login and branded-email tests stay green; a test proves sends carry the configuration set.
