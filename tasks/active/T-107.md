# T-107: Two-sided agreement and close, with e-signature

Model: opus
Engine: claude

**Lane:** core
**Context:** deep
**Touches:** prisma schema (headline price term, signatories, sign-offs, closing checklist, signature envelopes), API (pricing and terms, close), connectors (signing provider: fixture + DocuSign), web (buyer terms, seller terms, Close tab), docs (ADR 0021 addendum or new ADR), e2e
**Needs:** T-105 and batch 1 (merged 2026-11-06): versioned term proposals, seller answers, Agreed. Live DocuSign signing is gated: Kumar supplies a DocuSign account and keys, and the loop never switches it on by itself.

## Kumar's ask (2026-11-07)

"With the Pacts built so far, can the Seller and Buyer negotiate via the platform and finally once the deal is consummated, can they agree and approve in the pack from both sides?" Then: "Write T-107 and start building it. Why can't we add DocuSign steps as well in?"

## What exists today

- **Negotiation rounds:**
  - The buyer proposes versioned terms.
  - The seller accepts, rejects or counters each term.
  - The buyer takes counters into the next version.
- **Agreed:** a version the seller fully accepts is marked Agreed and frozen.

## The gaps this closes

1. **The headline price is not a term.** Terms only cover adjustments: price reductions, escrows, indemnities, retention, earnout and the seller note.
2. **There is no final sign-off by both sides with a named approver on each.**
3. **Only the buyer can propose.** The seller can only counter.
4. **Closing is one-sided.** It is a buyer stage change; the seller never confirms completion.
5. **There is no shared closing checklist, and no e-signature.**

## Scope

1. **Headline price as a term.** Every version leads with the equity purchase price (amount and basis), taken from the adopted evaluation's weighted price. The seller can counter it like any other term.
2. **Seller-initiated proposals.** A seller contributor may draft and propose a version of their own. The other side answers it with the same accept, reject and counter flow, and versions alternate.
3. **Named signatories.**
   - **Buyer:** the deal lead, or a member the lead names.
   - **Seller:** a contributor the seller side names.

   Both are recorded on the pact and audited.
4. **Dual sign-off.** An Agreed version needs an explicit approval from both signatories, each recorded with name and time. Either side may decline before signing, which reopens the round.
5. **Closing checklist.**
   - **Items:** conditions to close (consents, funds flow, documents, regulatory filings). Either side adds them; each is owned by a side.
   - **Ticking:** each item is ticked by its owning side, with who ticked it and when.
6. **Close.** The pact moves to Closed only when both of these hold:
   - the agreed version is signed off by both signatories;
   - every checklist item is ticked.

   The close records the date and both approvers. It replaces today's one-sided stage change for buyer-led pacts.
7. **E-signature, behind an adapter.**
   - **Interface:** a `SigningProvider` (create an envelope, check its status, take a webhook) in `packages/connectors`.
   - **Fixture adapter:** used by tests, dev and demos.
   - **DocuSign adapter:** the eSignature REST API v2.1, with JWT grant, envelope with recipients, and Connect webhooks. Built against DocuSign's current official docs and verified, never invented.
   - **What is signed:** a term sheet Pactlab generates from the agreed version (headline price and every term). Optionally, a final agreement uploaded by either side.
   - **Effect on sign-off:** both signatures complete equals the dual sign-off.
   - **Live DocuSign:** gated on Kumar's account, integration key, RSA key and account id, supplied via environment and secrets at go-live.

## Guardrails

- **Buyer-confidential stays buyer-confidential.** No persona, pricing parameter or finding reaches the seller, the term sheet or the envelope.
- **Humans decide.** Nothing auto-signs, auto-closes or auto-accepts.
- **Frozen.** Signed versions, sign-offs and ticked items are append-only or frozen once done. Every step is audited.
- **Money.** Decimal amounts with explicit currency.

## Acceptance

- **Full deal:** a buyer-led pact runs through to close with both sides:
  1. The buyer proposes, including the headline price.
  2. The seller counters the price.
  3. The buyer revises.
  4. The seller accepts.
  5. Both signatories sign off, via the fixture e-signature.
  6. The checklist is completed by both sides.
  7. The pact is Closed with both approvers recorded.

  Covered by API and e2e tests.
- **Seller-initiated:** a seller-initiated version is answered by the buyer.
- **Refusals:**
  - closing with an unsigned version or an open checklist item is refused;
  - a non-signatory cannot sign off;
  - other tenants are denied.
- **Leak test:** the seller and envelope outputs contain no buyer-confidential data.
- **DocuSign adapter:** contract tests against recorded fixtures. A live smoke test runs only when keys are present.
