# T-125 — No silent failures: every background job tells the person what happened

Model: opus
Engine: claude

**Lane:** platform
**Context:** standard
**Touches:** apps/api (every fire-and-forget job and `.catch` that only logs), apps/web (the pages that start those jobs: status and messages), packages/db (a job status where one is missing), docs (a short convention note in docs/agent or an ADR)
**Needs:** nothing open.

## Why

Kumar (2026-11-14), after Settings → Brand → "Fetch again" did nothing on live: "When something fails, we need to inform the user with some friendly message. That is also missing. Bad design."

The cause (fixed in #194): a background job caught its own error, logged it, and left the old state on screen. The person saw nothing happen. The same pattern exists elsewhere: work started "in the background" or in a `void …catch(log)` whose failure reaches only the server log.

## The rule (to adopt and enforce)

Any work the person started and that finishes after their request returns must end in one of these, and the page that started it must show it:
- **done:** with what changed;
- **failed:** with a plain sentence saying what went wrong, that nothing was lost (when true), and what to do next (try again, an alternative, or who to ask);
- **still running:** with an honest wait state, stopping after a bound with "this is taking longer than usual".

The server log keeps the technical detail; the person never gets a stack trace, an error code alone, or silence.

## What

1. Go through every row above, plus a search for `void …`, `.catch(() => undefined)`, `.catch((error) => log…)` and background `running` sets in `apps/api` and the worker. For each, decide what the person should see, and build it: a status field, a page message, a retry action.
2. Write one shared pattern for the web: a wait state with a bound, a success line, a failure line with the next step. The brand card's `BrandFetchWait` is the model; reuse it, don't fork it.
3. Write a guard so new silent failures don't slip in: a lint rule or a test that flags `.catch` handlers in `apps/api/src` that only log, unless the line carries a reviewed `// silent-ok: <reason>`.
4. Tests: for each fixed flow, an API test that forces the failure and asserts the person-visible status or message.

## Acceptance

- Every row is either fixed (person-visible outcome, tested) or marked `silent-ok` with a reason in the code.
- The guard fails CI on a new log-only `.catch` in `apps/api/src`.
- No message shows a raw error, a code alone, or nothing.
