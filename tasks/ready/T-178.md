# T-178 — Document prep bench: drop everything, convert to Pactlab's standard, check it, stage it, inject it into a pact

Engine: claude
Model: opus
Lane: platform
Context: deep
Touches: apps/web apps/api packages/connectors packages/ai packages/domain packages/contracts docs tasks
Needs: none
Checks: pnpm lint && pnpm typecheck && pnpm test && pnpm test:integration && pnpm test:fixtures && pnpm test:e2e

## Why

Kumar's concept (2026-11-26): a tool where the user drops **all** the documents for a deal, the tool converts them into the standard format Pactlab likes, checks them, and then puts the finished set into a deal room or OneDrive — ready to be injected into a pact. Today the document pipeline starts at a tidy connected folder (T-098/T-126/T-147 pull read-only from Drive/OneDrive/Box); real deal documents arrive as scans, photos, docx, odd PDFs and duplicates with chaotic names. The bench is the missing front half: it makes a document set deal-ready **before** it touches a pact, which raises extraction and citation quality for everything downstream.

## The flow: drop → convert → check → stage → inject

1. **Drop.** A bench workspace (usable before any pact exists, and from inside a pact) accepting bulk upload: many files at once, zip archives, the formats deals actually arrive in (PDF, docx, xlsx/csv, images/scans, email exports). Large sets process as background jobs with per-file progress, resumable on failure.
2. **Convert.** Every document becomes Pactlab's canonical form — a normalized PDF with extracted text and stable page anchors (the representation the citation engine cites) — plus structured metadata (title, date, type, counterparty) and a normalized name (date_type_counterparty). **Routing rule:** spreadsheets and statements are not flattened into documents; they are routed to the guided-import flow (T-152) so financials land as data. Scans and images go through the vision lane (T-121) for OCR quality. **Originals are preserved untouched** alongside every converted version, with a per-file conversion log (what was done, by which model/tool, when).
3. **Check.** Per file: readable vs corrupted, OCR/extraction quality score with a clear below-threshold flag, exact and near-duplicate detection, and classification into the pack's document taxonomy (the user confirms or corrects the type — the T-094 review-queue pattern). Per set: **completeness against the target pack's expected-document list**, producing explicit missing-item flags ("2023 audited financials — not in set") instead of silent gaps. Files with errors or unconfirmed warnings sit in the review queue; **nothing with an unresolved error is injectable.**
4. **Stage.** The approved set is written to the destination the user picks: a folder in OneDrive, Google Drive or Box, or an internal deal-room folder. **Write access is a new, separate connection**: an explicitly granted, staging-only connection whose token is scoped to the single folder the user chose — proven by a scope-pinning contract test in T-147's style. The existing read-only source connections are untouched and their guarantee stands: Pactlab never writes to a source folder.
5. **Inject.** From staging, the set injects into a pact two ways, user's choice: (a) connect the staged folder as the pact's document source through the existing OAuth sync (T-147), so later changes keep flowing; or (b) one-time injection of the converted set into the pact's documents. Injection records provenance per document (bench batch, original file, conversion log) so any finding's citation can trace back to the original upload.

## Who uses it

- **Buyer/deal team:** preps a received data-room dump before creating or feeding the pact.
- **Seller/guest side:** an invited guest can prep and stage *their* documents in the bench without any access to the pact; the buyer reviews the checked set and injects it. The confidentiality walls are untouched — bench content is visible only to its owner and invited bench collaborators until injection, and injection is always the pact-side user's explicit act.

## AI and gates

Classification, metadata extraction and OCR-quality scoring are AI jobs through the gateway (JOB_MODEL_MAP entries, fast lane default, cost metered per file against the AI budget); ADR 0034 data-terms and evaluation gates apply as for every job. Deterministic checks (corruption, hashes, duplicates by hash) never spend model calls.

## Checks

- End-to-end: a mixed fixture set (scan, docx, xlsx statement, duplicate, corrupt file) → statements routed to import, documents converted with page anchors, duplicate and corrupt file flagged and blocked from injection, the rest staged and injected with provenance.
- Scope test: the staging connection cannot write outside its folder (a write attempt elsewhere fails at the adapter).
- Wall test: a guest's bench content is invisible to the pact side until injection.

## Acceptance

- A user drops a messy 20-file set, resolves two flags in the review queue, stages it to OneDrive, and injects it into a pact — every resulting document citable to its original upload.
- The completeness panel names the pack-expected documents missing from the set.
- The read-only source connections behave exactly as before (existing suites green).
