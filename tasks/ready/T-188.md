# T-188 — Multifamily property profile: RentCast property records + Google photos, auto-populated by address

Engine: claude
Model: sonnet
Lane: platform
Context: standard
Touches: packages/connectors packages/config packages/domain packages/db apps/api apps/web docs tasks
Needs: none
Checks: pnpm lint && pnpm typecheck && pnpm test && pnpm test:integration && pnpm test:fixtures && pnpm test:e2e

## Why

T-158 wired only RentCast's rent-estimate endpoint (rents against the market). Kumar (2026-11-27) wants the multifamily pack's property profile itself auto-populated from the property's address: the public-record metadata and pictures, without the user typing what a service already knows. RentCast's property-records endpoint has the metadata (same vendor, same API key — it was simply never wired); RentCast serves no photos, so photos come from Google Maps Platform, the one photo source that covers all Pactlab launch markets.

## Build

1. **RentCast property records in the existing property connector** (`packages/connectors/src/property`, beside the T-158 adapter): `GET /v1/properties` by address and `/v1/properties/{id}`. Map the record into the multifamily property profile: property type, living area, lot size, year built, features (parking, construction materials, heating/cooling, floor/room counts), tax assessment history, tax history, sale history, and current owner (name, type, mailing address, owner-occupied). Every populated field carries provenance — source (RentCast public record), the record's own identifiers, and fetched-at — and renders labelled as third-party reference data wherever it appears.
2. **The populate flow:** on a multifamily pact, the user enters or confirms the property address → the profile is prefilled from the record → the user reviews, edits and accepts. Accepted values become pact data with their provenance attached. Reference data never silently overrides evidence: where a seller document or an import later contradicts a populated field, the document wins and the contradiction surfaces as a finding input (the claims-vs-evidence pattern), it is not auto-resolved.
3. **Honest absence:** RentCast field coverage varies by county. A field the record lacks shows as "not in public record", never blank-filled or guessed. Sale prices are unavailable in non-disclosure states (Texas among them): show "sale price not published (non-disclosure state)", never zero and never an estimate dressed as a record.
4. **Photos via Google Maps Platform** (new env `GOOGLE_MAPS_API_KEY`, distinct from the Gemini `GOOGLE_API_KEY`; pay-as-you-go, calls metered like other providers): Street View imagery for the address (exterior, with its capture date shown) plus Places photos when the property matches a Google place (most apartment communities do), displayed in the property profile gallery with the attribution and source labels Google's terms require, fetched and cached server-side within those terms. Photos are illustrative reference material, labelled with their source and date — they are never diligence evidence and never enter findings.
5. **Market honesty:** metadata population is offered for US addresses only (RentCast's coverage); for non-US addresses the button explains that and the profile stays manual/import-driven. Photos are offered wherever Street View/Places coverage exists (all launch markets; Indian metros). No market gets a fake or scraped substitute.
6. **Demo and tests:** the multifamily demo property's profile is populated from recorded fixtures (cassettes) of both providers — CI never calls the live APIs, per the house rule. Fixtures include a Texas property (non-disclosure sale price) and a record with missing fields.

## Acceptance

- Entering a US multifamily address populates the profile (type, area, lot, year built, features, tax and sale history, owner) with per-field provenance labels, after user review-and-accept.
- The Texas fixture renders its sale price as not published (non-disclosure), and a sparse-record fixture renders missing fields as "not in public record".
- The profile gallery shows the Street View exterior (with capture date) and Places photos with attribution; a pact whose imported rent roll contradicts a populated field raises the contradiction as a finding input rather than overwriting either side.
- A non-US address gets the honest explanation and no population attempt.
