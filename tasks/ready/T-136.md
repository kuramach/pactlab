**Amendment (Kumar's decision, 2026-11-18): provider seam, BoldSign first.** Pricing research changed the provider plan. DocuSign's self-serve API plans do not cleanly cover Pactlab's case: embedded signing inside our own product for our customers is an "Embedded integration" requiring sales-led ISV licensing, and account-level Connect webhooks sit in the $480/mo Advanced API tier. BoldSign (Syncfusion) covers the same ground on a pay-as-you-go plan: $30/mo including 40 envelopes, then $0.75 per envelope, with embedded signing and webhooks included and no go-live review. So signing gets the T-132 treatment: a provider seam with one contract, BoldSign as the launch adapter, and a DocuSign adapter deferred until an enterprise customer justifies the ISV path.

## Build

1. **Signing-provider seam.** A provider-neutral signing contract in the platform (the T-132 registry/seam pattern applied to signing): create an envelope from a pact document, open an embedded signing session for a guest signer, read envelope status, fetch the signed artifact and the completion certificate/audit trail. The provider is chosen per organization (item 9); no provider-specific types leak into pact or domain code. Contract tests define the bar every adapter must pass.
2. **BoldSign adapter — the only adapter in this task.** Counterparties sign inside an embedded BoldSign session launched from Pactlab — no Pactlab account required, consistent with the guest model (sellers are passwordless; identity for signing is the email invitation + the provider's embedded-session flow). The buyer-side user sends and tracks from within the pact. BoldSign webhooks drive status; polling is the fallback for a missed webhook, never the primary path.
3. **Envelope creation from Pactlab documents.** First surface: the T-119 LOI (generated from agreed terms, drafts private until sent — that rule is unchanged). The design must generalize to other pact documents (approved terms documents, IC-approved packages) without rework: a document -> envelope service behind the seam, not an LOI-only hack.
4. **Status as pact state.** Envelope status (sent / delivered / signed / declined / expired / voided) is pact state, driven by provider webhooks (idempotent handlers; polling fallback). Status changes land in the pact timeline.
5. **Signed artifact as evidence.** On completion, the signed document and the provider's certificate of completion / audit trail are stored in the pact as evidence — the signed file preserved byte-for-byte as the legal artifact (the same principle as T-089's original-file rule). Declines and expiries are recorded with reason where the provider provides one.
6. **T-119 wiring.** LOI exclusivity expiry tracking (already in T-119) reads the real signing state: an envelope expiring unsigned surfaces against the exclusivity clock, not as a silent dead end (T-125 no-silent-failures rule).
7. **Config.** Provider credentials live in env/secret config per environment, like the existing provider settings: SIGNING_PROVIDER sets the deployment's default and allowed adapters (e.g. `fixture` in dev and tests); the BoldSign adapter reads BOLDSIGN_API_KEY and BOLDSIGN_API_BASE_URL (default https://api.boldsign.com, the US region). Webhook signature verification reads BOLDSIGN_WEBHOOK_SECRET, registered once a deployed environment has a public endpoint; until then the polling fallback carries status in dev. No envelope is ever sent from a non-live environment to a real counterparty address — sandbox envelopes go to test recipients only.
8. **Live wiring for testing.** Following the AI-provider-key pattern in infra/cdk (compute.ts secrets + scripts/ai-key.sh), wire SIGNING_PROVIDER and the BoldSign secret into the deployed environments' config — live included, per the Live testing note above — with a scripts/signing-key.sh-style helper that sets the key value per environment. Until the production go, live uses the SANDBOX account and envelopes go only to test recipients (Kumar's own addresses); swapping in the production key is the later, separate go.
9. **Signing provider per organization (Kumar, 2026-11-18).** The organization's owner or admin chooses it in Settings → Signing.
   - **Pactlab signing (BoldSign):** the default. Pactlab's own account, nothing for the customer to set up.
   - **Your DocuSign:** offered only once the organization has connected its own DocuSign account (the existing T-107 adapter and connection, moved onto the seam as a second adapter and passing the same contract tests).
   - **Recording:** each envelope records the provider it was sent with. Changing the setting affects new envelopes only; envelopes in flight finish on their own provider. A disconnected DocuSign account falls back to the default for new envelopes and says so; it never fails silently.
   - **Audit:** the change is audited, and server-side checks enforce who may make it (owner or admin only).
   - **Scope:** no new DocuSign work beyond moving the adapter. The ISV embedded-licensing path stays deferred until an enterprise customer justifies it.

## Acceptance

- End to end on the BoldSign sandbox: an LOI generated in a pact is sent for signature from within Pactlab; a guest signer completes it in an embedded session; status transitions appear in the pact timeline via webhook; the signed PDF + certificate are stored as pact evidence, byte-for-byte.
- The seam holds: pact/domain code contains no BoldSign-specific types, and switching provider is a setting, not code: both adapters pass the same contract tests, an organization moves between Pactlab signing and its own connected DocuSign in Settings, and each envelope keeps the provider it was sent with (tests).
- Webhook idempotency proven by test (duplicate delivery changes nothing twice); polling fallback proven by test (webhook suppressed, status still converges).
- A declined and an expired envelope each land in the pact record with their status visible — no silent states.
- Tests run against the BoldSign sandbox or recorded fixtures; CI never sends a real envelope (CLAUDE.md: CI never calls live third parties for gating tests).
- Live smoke (Kumar, after deploy): an LOI sent from the live app to a test recipient is signed in an embedded session, and its status transitions + signed artifacts land in the pact — sandbox account, no real counterparty addresses.
