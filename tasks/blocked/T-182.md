## What to build
- **A Pactlab LINE Official Account** with a Messaging API channel. Kumar's one-time setup (LINE Developers console; channel secret and access token into Secrets Manager) goes in the runbook as a short checklist.
- **Linking, on "Your profile":** **Connect LINE** uses LINE Login (OAuth 2.0 / OpenID Connect) to get the person's LINE `userId`, then prompts them to add the official account as a friend; push messages reach only friends.
  - Store the `userId` against the person only after both steps.
  - Unfollowing the account (the `unfollow` webhook event) disconnects at once.
- **Webhook security:** verify every webhook with the `x-line-signature` header, an HMAC-SHA256 of the body using the channel secret.
- **Sending:** a push message that's content-free, the same rule as T-146.
  - Wording in Japanese for `ja` users, using T-172's catalog when present; otherwise both English and Japanese.
  - No pact name, party, amount or document text.
- **Connector seam:** behind it, with a fixture adapter; off by default.
- **Verify first:** check every endpoint, event, header and limit against developers.line.biz before writing code. Invent nothing.

## Rules
- A LINE `userId` is personal data: never sent to a model, logged or put in a fixture. RLS by user and organization; changes audited.
- T-146 routes "act now" alerts to LINE like the other channels, with the same per-person cap and the same 15-minute fold.

## Acceptance
- With the fixture: connect via LINE Login, add as a friend, get a content-free test message; `unfollow` disconnects and nothing more is sent.
- A webhook with a bad signature is rejected.
- At the monthly cap: no LINE send, an email fallback, and an admin notice.
- Tests prove no pact content reaches a LINE payload.
