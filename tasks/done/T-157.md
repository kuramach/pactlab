# T-157 — Log triage for dev, qa and stage: same sweep as live, pre-production bug list for the same triage

Engine: claude
Model: opus
Lane: platform
Context: deep
Touches: infra/cdk docs .github/workflows scripts
Needs: T-150

**Needs note:** This task extends T-150's machinery (clustering, scrubbing, triage state, digest, GitHub issues, the triage-to-task workflow) to the pre-production environments. It starts only after T-150 is in tasks/done/ — do not rebuild the pipeline; parameterize and deploy it per environment.

## Why

T-150 gives live a daily error sweep: CloudWatch errors clustered, Bedrock verdicts, one email digest, GitHub issues for triage. Kumar's direction (2026-11-25): dev, qa and stage get the same treatment, so bugs surface where they are introduced instead of first being seen in live. Same rules as T-150: everything runs in AWS, never on the Mac; review reaches Kumar by email and GitHub; nothing becomes a task without his triage-approved label.

## Build

1. **Generalize T-150's sweep by environment.** The Lambda, state store, clustering, scrubbing, reportability thresholds and digest rendering from T-150 take the environment as configuration (log groups, account, labels, secret names, recipient). One deployment per account: the dev account sweeps BOTH the dev and qa environments (both live in that account, separate log groups and separate triage state per env); the stage account sweeps stage. Live is untouched — T-150's deployment keeps working exactly as built.
2. **Log inventory and retention.** Same as T-150 step 1 for the dev, qa and stage log groups (api, worker, web per env): CDK sets retention of at least 30 days. This matters more here than in live — these envs sit idle-paused for long stretches, and the watermark sweep must still find the errors a short wake produced.
3. **Idle-pause aware sweeping.** Same daily EventBridge schedule and watermark logic. A paused env simply yields nothing reportable — silence stays healthy, no "env was quiet" email. The first sweep after a long pause covers since-the-watermark, capped the same way T-150 caps its window.
4. **Bedrock triage, with the dev-account exception.** Stage classifies exactly like live (stage Bedrock verified working 2026-11-20). The dev account's Bedrock access is NOT enabled yet (Kumar's open item), so the dev-account deployment ships in cluster-only mode for dev and qa: clusters, counts, first/last seen, scrubbed samples, verdict shown as "unclassified — Bedrock not enabled in this account". No cross-account Bedrock calls — the moment dev Bedrock is enabled, the same deployment flips to full verdicts by configuration alone (the account's default Claude alias, as in T-150), with no code change and no redeploy of anything else. Document the flip in the runbook.
5. **Digest.** One digest email per account per day, only when that account has something reportable (same silence rule), sent via that account's SES to the configured recipient (default kumar@pactlab.ai), clearly sectioned per environment — dev findings never mixed into qa's. Noise/unclassified sections follow T-150's audit pattern. If an account's SES is still sandboxed, verifying the recipient identity is an activation step (see prerequisites) and is documented in the runbook.
6. **GitHub issues.** Same flow as T-150 step 6, env-scoped: title "[env-triage:<env>] <summary>", labels `env-triage` and `env:<env>`, body identical in shape to live-triage issues (counts, first/last seen, scrubbed samples, verdict, fix sketch, Insights query). The dedupe signature marker includes the environment — the same signature in dev and in live stays two separate issues. Credential: an issues-write-only fine-grained token per account, held in Secrets Manager as `pactlab/<env>/github-triage` in that account and loaded with the same scripts/ helper pattern as T-150 (one token value may be stored in both accounts — the helper supports it).
7. **Approval becomes a task.** Extend T-150's triage-to-task workflow so the `triage-approved` label on an `env-triage` issue files a house-format task exactly as it does for live-triage (next free T-number, body carries the cluster detail and the environment, issue commented with the task ID, `task-filed` label applied). One workflow, both label families.
8. **Docs.** Extend docs/runbooks/log-triage.md with the per-env deployments, the dev cluster-only mode and its Bedrock flip, SES state per account, and the pause procedure per schedule. A short ADR addendum (or a section in T-150's ADR) recording that pre-production triage reuses the live pipeline rather than forking it.

## Kumar prerequisites (do not block the build; they gate activation per env)

- Load the GitHub triage token into the dev and stage accounts' secrets with the helper from step 6 — gates real issue creation per account.
- Dev Bedrock enablement (already open with Kumar: first-use form plus one CLI Converse in the dev account) — gates only the dev/qa AI verdicts; cluster-only mode works without it.
- Approve each account's dry-run digest before that account's email and issue creation switch on.
- If an account's SES is sandboxed, verify kumar@pactlab.ai as a recipient identity there (one confirmation email) so the digest can send.

## Guardrails

- Same as T-150, per account: each Lambda's role is read-only on that account's env log groups only, Bedrock invoke on the triage model only (where enabled), SES send to the configured recipient only, read/write on its own triage state. No write access to any application resource, no cross-account roles.
- Same scrubbing as T-150 before anything leaves AWS; never request bodies in an email or issue.
- No task file is ever created without Kumar's triage-approved label; this system never opens fix PRs.
- Pay-as-you-go only: watermark-scoped queries, Bedrock calls capped per run (default top 10 reportable clusters per env), no standing compute beyond the scheduled Lambdas.
- Nothing depends on the Mac; approved tasks wait in tasks/ready/ like any other.

## Checks

- Unit tests: env configuration resolution (dev account resolving both dev and qa), per-env dedupe markers, cluster-only mode rendering (verdict absent, digest still correct), the workflow's handling of env-triage issues including the environment in the filed task body.
- CDK synth/snapshot tests for the new per-account resources and Lambda roles.
- Dry-run mode per env (env flag, as in T-150): queries run, digest and issue bodies written to the Lambda log, nothing sent or opened. Dev/qa dry-runs exercise cluster-only mode; stage's dry-run exercises full Bedrock verdicts.

## Acceptance

- Dry-run digests for dev, qa and stage produced from real log data and reviewed by Kumar — dev/qa in cluster-only mode, stage with verdicts.
- After Kumar loads the tokens and gives the go per account: one real run per account sends at most one digest and opens deduped env-triage issues.
- Labelling an env-triage issue triage-approved produces a valid task file in tasks/ready/ via the extended workflow, with the environment named in the task body.
- Runbook updated (per-env pause, token rotation, the dev Bedrock flip); enabling dev Bedrock later requires no code change to activate verdicts.
