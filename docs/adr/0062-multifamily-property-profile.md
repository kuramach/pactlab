# ADR 0062: Multifamily property profile from public records and Google photos (T-188)

**Status:** accepted (Kumar asked for it, 2026-11-27).

## Context
- T-158 (ADR 0045) wired only RentCast's rent-estimate endpoint. A multifamily pact's property profile (type, area, year built, taxes, sales, owner) was still typed by hand.
- RentCast's property-records endpoints hold that metadata under the same key. RentCast serves no photos. Google Maps Platform (Street View Static, Places) is the one photo source that covers every Pactlab launch market, Indian metros included.
- Public-record data is third-party reference data. It is not a seller statement and not a document in the data room.

## Decision
1. **Property records behind a seam.** `PropertyRecordProvider` in `@pactlab/connectors`: `RentCastPropertyRecordProvider` (live: `GET /v1/properties?address=` then `GET /v1/properties/{id}`, key in `X-Api-Key`) and `FixturePropertyRecordProvider` (synthetic). The record is normalized to the domain's `PublicRecord`; every field is optional because county coverage varies.
2. **Photos behind a seam.** `PropertyPhotoProvider`: `GoogleMapsPhotoProvider` (live) and `FixturePhotoProvider`. Street View: the metadata call (capture date, pano id) then the image. Places (New): text search, accepted only when the hit's street number and street name match the address, then the photo media. Env `GOOGLE_MAPS_API_KEY`, distinct from the Gemini `GOOGLE_API_KEY`. Pay-as-you-go: every provider call is one audit event (`property_profile.record_fetched`, `property_profile.photos_fetched`), which is the metering record.
3. **Populate, review, accept.** On a multifamily pact the user enters or confirms the address; `POST …/property-profile/populate` fetches the record and stores it as *proposed*. Nothing is pact data until the user accepts it (`…/accept`), editing what is wrong. An accepted value keeps the record's provenance (source "RentCast public record", the record's own id, fetched-at) and a basis: kept as the record gave it, edited, or entered by hand. The label "Third-party reference data" renders on every row it appears on.
4. **Honest absence.** A field the record lacks reads "not in public record". A missing sale price in a non-disclosure state (AK, ID, KS, LA, MS, MO, MT, NM, ND, TX, UT, WY) reads "sale price not published (non-disclosure state)". The absence text can never be accepted as a value. The state list is a display rule, not legal advice; a sale price absent anywhere else is "not in public record".
5. **Reference data never overrides evidence.** `contradictionsWithRentRoll` compares accepted values with the imported rent roll (unit count must agree; the rent roll's rentable area may not exceed the recorded building area). A contradiction becomes a `deal_claims` row (origin `PACK_RULE`, status `CONTRADICTED`, citing the rent roll's units), the same claims-vs-evidence path as the pack's other checks. Neither side is changed. It runs when values are accepted and on "Check against the imported rent roll".
6. **Photos are illustrative.** They are stored as references (kind, source, capture month, attribution), never as image bytes, and never enter evidence or findings. The browser asks Pactlab's API for a photo by its position in the pact's own gallery; the API fetches the bytes from Google server-side, so the key never reaches the browser, and passes them through (`private, max-age=3600`, `nosniff`, sandboxing CSP). Pactlab stores no Google image content; only the Places photo references, which Google lets an application keep, and which may expire (the user re-runs "Find photos"). Street View shows its capture month; Places photos show the author attribution and link Google requires, and the gallery carries "Imagery © Google".
7. **Market honesty.** Metadata is offered for US addresses only (RentCast's coverage); `addressCountry` reads a US state and ZIP, or "USA". For anything else the API answers `METADATA_US_ONLY` before any provider call and the page says why; the profile stays manual and import-driven. Photos are offered wherever Google has coverage. No scraped or invented substitute for any market.
8. **Who.** Buyer side only (`BUYER_ANALYSIS_READ` to read, plus `DEAL_WRITE` to fetch, accept or check). A counterparty gets 403 and another tenant 404. The profile holds the owner of record, so every read is audited (`property_profile.viewed`). The owner data goes to no model and no embedding.
9. **Storage.** `deal_property_profiles`, one row per pact with organization and deal identity, RLS buyer-side only (migration `20270119000000_property_profile`, expand only). Rollback: drop the table.
10. **Fixtures.** `fixtures/cassettes/rentcast/properties-synthetic.json` and `fixtures/cassettes/google-maps/photos-synthetic.json` replay the live adapters in tests; the fixture providers hold the same records (a test keeps them identical). Included: a Texas record without sale prices and a sparse record. The multifamily demo pact's profile is populated from the Texas fixture. CI never calls RentCast or Google.

## Consequences
- The Google endpoints and field names were written from Google's references as read on 2026-11-27 and are covered by cassettes built from those references, not live recordings. Before the first live key is set, check one live address against the runbook's checklist.
- The CDK secret and task wiring for `GOOGLE_MAPS_API_KEY` is a separate infrastructure task (CDK is out of this task's scope). Until it lands, production has no photos and says so.
- Photo references can expire; the gallery says "found <date>" and offers a refresh.
- Operating: `docs/runbooks/rentcast.md`.
