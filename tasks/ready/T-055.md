## Why (found in review)

- **Silent truncation.** The engineering API reads at most 50,000
  contributor-activity rows (`MAX_ROWS`); 3,000 people × 24 months × code +
  delivery ≈ 144,000, so most of the team would be missing with no warning.
  GitHub activity also stops at `MAX_ACTIVITY_COMMITS` = 50,000 per repository
  (reported as an issue, but reachable).
- **Quadratic calculation.** `engineeringReport` filters the full activity
  list once per contributor (≈ 3,000 × 144,000 steps per page load).
- **UI built for a small team:** the code-vs-delivery map (labelled bubbles),
  the ownership network (every person and area), the details table and keep
  list (all rows on one page) and the areas bar chart (every area).

## Work

1. **Correct at scale.** Read activity in batches with no silent cap; if the
   data is incomplete (connector truncation, unreadable sources), say so on
   the page. Rewrite the calculation to group by contributor once (linear).
   Same rules: deterministic `engineering-N` version bump, no score or rank,
   cohort < 5 suppressed, never sent to AI.
2. **API.** `GET /v1/deals/:id/engineering` returns team aggregates, a compact
   point list for the map, and the keep list with its count. New paged
   `GET /v1/deals/:id/engineering/people` with search (name or pseudonym),
   tag and area filters. Name gating and `people.names_viewed` auditing apply
   to both, unchanged.
3. **Map.** Above ~150 people: no labels, small points, large-data rendering,
   zoom and pan, a search box that highlights one person, tag and area
   filters.
4. **Network.** Up to ~60 people: the full graph as now. Above: areas plus key
   people only (sole owners and owners), everyone else as a count on each area;
   clicking an area expands its people.
5. **Details, keep list, areas.** Server-paged details table with search and
   filters; keep list shows the first 20 with "Show all (n)"; areas chart
   shows the 25 busiest plus "Other", and lists every single-maintainer area.
6. **Synthetic ScaleCo** (~3,000 engineers, ~40 areas) in the GitHub and Jira
   fixture sources, reachable through Sources → synthetic data, so the UI can
   be checked at size.

## Tests

- Calculation: identical results to the current version on the existing
  fixtures (except the version id); a 3,000-person / 144,000-row input
  completes within a stated budget; no truncation.
- API: totals over > 50,000 activity rows are complete; paged people endpoint
  (search, filters, paging) with names hidden and shown; audit on name views;
  target contributors denied.
- Web: thresholds switch map and network modes; paged table and keep list.

## Out of scope

- Many repositories per deal (a 3,000-person company has hundreds; today one
  GitHub connection is one repository) — a separate task. This design must
  work unchanged once it exists.
