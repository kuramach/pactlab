# T-156 — Auto-start the agent loop when Claude usage is available again

Engine: claude
Model: sonnet
Lane: platform
Context: standard
Touches: scripts docs
Needs: none

## Why

When a run hits Kumar's Claude usage limit, run-task.sh already does the right thing: it pushes a WIP commit, returns the task to ready/ and exits 75 so the loop stops (PR #234). But nothing restarts the loop when usage comes back — Kumar has to notice and relaunch by hand. His direction (2026-11-24): the loop should start itself when Claude usage is available again. The Mac mini is a dev machine and may sleep; the mechanism must be patient, cheap, and safe to fire when usage is still exhausted.

## Build

1. **Usage probe.** A tiny headless Claude call (`claude -p "Reply with the single word OK"` with the loop's usual flags) is the availability test: at the limit it fails immediately with the limit error and consumes nothing; a successful reply means usage is back. No queue state is touched by the probe.
2. **Wrapper script `scripts/loop-autostart.sh`.** Behaviour, in order:
   - Exit silently if an agent-loop is already running (pgrep on agent-loop.sh) — never run two loops.
   - `git pull --ff-only` in the repo so the loop sees the current queue.
   - Run the probe. If it fails, log one line with the timestamp and exit 0.
   - If it succeeds, start the loop detached with the standard environment (`CLAUDE_FLAGS=--dangerously-skip-permissions`, `--auto-merge`) under `caffeinate -i` so the Mac doesn't idle-sleep mid-run, appending to a log file under `~/Library/Logs/pactlab-loop/` (or a repo-ignored logs path — builder's choice, documented).
   - Resolve `claude`, `git` and `caffeinate` robustly under launchd's minimal environment: the install step records the Mac's real paths (Homebrew locations) into the generated plist/wrapper config — no assumptions about PATH.
3. **launchd agent.** A plist template (`scripts/launchd/ai.pactlab.loop.plist`) with label `ai.pactlab.loop`, `StartInterval` 1800 (probe every 30 minutes) and `RunAtLoad` true, invoking the wrapper. Plus an install/uninstall section in the runbook with the exact commands (bootstrap/bootout against the user's GUI domain) — installing it is a one-time manual step for Kumar; this task ships the template and verifies it parses (`plutil -lint`) and that the wrapper behaves correctly when invoked by hand.
4. **Runbook** (`docs/runbooks/loop-autostart.md`): how it works, how to check the log, how to pause it (bootout), how to change the probe interval, and the failure modes — Mac asleep (launchd runs the missed job on wake), weekly usage cap (probes keep failing until the weekly reset; nothing to fix), and a probe that succeeds while the queue is empty (the loop starts, drains instantly, exits — harmless).

## Guardrails

- The probe must never claim, move or modify a task; only the loop itself does that.
- Never two loops: the pgrep guard is tested, including the case where a loop is running but idle.
- A failed `git pull` (dirty tree, conflict) aborts the start and logs why — the wrapper never forces, stashes or resets.
- The autostart does not change the loop's own gates: usage-limit parking (exit 75, WIP commits) and Touches/Needs claiming rules work exactly as today, and a restarted task resumes from its WIP commit as run-task.sh already supports.

## Checks

- Wrapper invoked by hand with usage available and no loop running: starts the loop.
- Wrapper invoked while a loop is running: exits, starts nothing.
- Wrapper's probe path with a stubbed failing `claude`: logs the failure, exits 0, starts nothing.
- `plutil -lint` on the plist template; shellcheck (or repo lint) clean on the wrapper.

## Acceptance

- Kumar runs the two install commands from the runbook once; from then on, when Claude usage returns after a limit stop, the loop restarts itself within one probe interval (30 min) and the interrupted task resumes from its WIP commit — with no human action.
