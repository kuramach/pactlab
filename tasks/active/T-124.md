# T-124 — Demo sync: synthetic data, the demo org and the demo instructions follow every change to pact structure

Model: opus
Engine: claude

**Lane:** platform
**Context:** standard
**Touches:** apps/api/src/ops (demo-org, demo-pool, a sync guard test), packages/domain (pact sections, demo-data pin), apps/web/lib/showcase.ts, apps/site/lib/try.ts, .github/workflows/deploy.yml (post-deploy demo refresh), scripts/demo-data (the synthetic data set), docs/runbooks/demo-org.md
**Needs:** nothing open.

## Why

Kumar (2026-11-14): when a release changes the structure of a pact (a new tab, a new evidence type, a new term or record), the demo must change with it. Otherwise a demo of the new release shows an empty tab, or instructions for a flow that no longer exists.

Today some of this follows the code and some does not:

| Part | Follows the code? |
|---|---|
| The demo builder (`apps/api/src/ops/demo-org.ts`) | It is code, so a feature can add its demo step (T-117 did, for Financing). Nothing makes it do so. |
| The five shared demo slots (T-113, ADR 0028) | Rebuilt from the current builder only when a share ends (the 15-minute sweep). An idle slot keeps the data of the release it was built on. |
| The main demo org (`pnpm demo:live`) | Never rebuilt on deploy: run by hand. |
| The guide copy (`apps/web/lib/showcase.ts`) | Enforced: a test fails when a pact section has no "Why this matters" copy. |
| The demo-org test's tab list | Hand-maintained, so a new section does not fail it. |
| The synthetic data set (`pactlab-demo` repo, pinned by `DEMO_DATA_COMMIT`) | Manual: a new import target or document type needs a new file and a new pin. |
| The site's "Try it" instructions (`apps/site/lib/try.ts`) | Manual, per pack. |

## What

1. **One guard test, derived, not listed.** It walks `DEAL_SECTION_RULES` and each pack's import targets, and fails CI when any of these lacks:
   - demo data on a built demo pact: the section's API returns something non-empty for the demo buyer, and where the section is two-sided, for the demo seller too;
   - guide copy (already enforced; folded into the same test);
   - a "Try it" step on the site for the packs where it applies;
   - a file in the pinned synthetic data set, for every import target the pack declares.

   A section can opt out only through a reviewed allowlist, each entry with a reason. Example: `/listing` on a buyer-led pact.
2. **A demo build version.** A hash of the builder, the pinned data commit and the section list is stored on each demo org and slot when it is built.
3. **Refresh on deploy** (`deploy.yml`, after the smoke test, dev and live):
   - when the deployed build version differs from a slot's, rebuild every **idle** slot (never one that is shared out; it rebuilds when its share ends, as today) and the main demo org;
   - report what was rebuilt in the job summary;
   - never block or fail the deploy: a failed rebuild is reported and retried by the next sweep.
4. **Synthetic data in step.** A checklist in `docs/runbooks/demo-org.md` covers a new import target or document type: add the file to `pactlab-demo`, bump `DEMO_DATA_COMMIT`, and run the guard. The guard names the missing file.
5. **Instructions in step.** The site's `/try/<pack>` steps are generated from, or checked against, the same section list, so a removed flow cannot keep its instructions.

## Guardrails

- Synthetic data only; never production data in the demo set.
- A refresh never touches a slot while it is shared, and never an organization that is not marked DEMO.
- Outward actions stay off in demos, as in T-113.

## Acceptance

- Adding a new pact section without demo data, guide copy or a "Try it" step fails CI, naming what is missing.
- After a live deploy that changes the builder, idle demo slots and the demo org show the new release's data without anyone running `pnpm demo:live`, and the job summary says so.
- A slot that is shared out during the deploy keeps its data until the share ends, then rebuilds on the new release.
