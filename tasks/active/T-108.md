# T-108 — Passkey sign-in for email-code organizations
Model: opus
Engine: claude

**Lane:** platform
**Context:** standard
**Touches:** packages/db (migration: passkeys, passkey challenges, SECURITY DEFINER functions), packages/db/src/login.ts, packages/contracts (auth), apps/api/src/email-login (passkey endpoints), packages/config (WebAuthn RP settings), apps/web (login page, Settings → Sign-in), docs (ADR, runbook)
**Needs:** nothing open. Plan approved before code (sign-in change). New dependency `@simplewebauthn/server` and `@simplewebauthn/browser` (open source, MIT, no paid service).

## Why

Stage and live sign in with a 6-digit email code only. Kumar asked (2026-11-07) for a faster, stronger option. Auth0 (T-104) comes later for SSO organizations; email-code organizations keep Pactlab's own sign-in permanently, so passkeys serve them for good.

## Shape

- **Add one:** a signed-in user adds a passkey in Settings → Sign-in. The device asks for Face ID, Touch ID or Windows Hello; a phone works over the browser's QR code.
- **Sign in:** "Sign in with a passkey" on the login page (and the browser's passkey autofill on the email field). No email, no code. The session is exactly what an email code gives.
- **Fallback:** the email code stays; losing a device never locks anyone out.
- **Manage:** the user sees their passkeys (name, added, last used) and removes any.
- **Auth0 organizations:** a passkey signs into email-code organizations only — the same rule as email codes.

## Work

1. Migration: `user_passkeys` and `passkey_challenges`, owned and reached only through `pactlab_auth` SECURITY DEFINER functions (the email-login pattern). Audited.
2. API: registration and sign-in ceremonies with `@simplewebauthn/server` v14; RP ID and origin from config per environment.
3. Web: login button and autofill, Settings card, server actions (the browser never holds the API token).
4. Security email on every passkey added or removed.
5. ADR and runbook; tests for allow and deny paths.
