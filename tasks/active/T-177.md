## Kumar's model (2026-11-26)

Per-deal pricing is **a fixed fee plus a variable that scales with deal size** — a $100M deal carries far more documents and complexity than a $10M deal, and one-size pricing ignores that. The variable is a small percentage of the deal's enterprise value on a declining scale, so it stays a modest addition, never the headline. This supersedes the earlier research position of never pricing as a percentage of deal value (docs/pricing-research.md is updated by this task to record the change and why).

## The schedule (config data in T-087's price book — Kumar tunes the numbers without code)

- **Fixed fee: $5,000 per pact** — the workspace, packs, evidence and findings machinery, with a base document/AI allowance.
- **Variable, on the deal's enterprise value:** 5 bps (0.05%) on the first $25M; 2 bps on $25M–$100M; 1 bp above $100M. **Variable capped at $50,000 per deal.**
- Worked totals: $10M deal → $5,000 + $5,000 = **$10,000**. $50M → $5,000 + $17,500 = **$22,500**. $100M → $5,000 + $27,500 = **$32,500**. $250M → $5,000 + $42,500 = **$47,500**. $500M → variable capped, **$55,000**.
- **Pilot stays flat $5,000, no variable** (the established pilot offer is unchanged).
- The variable carries the scale it prices: the included document count and AI budget for the pact step up with the variable bands (the actual cost driver), shown to the buyer at checkout as what's included.
- Venture Raise uses the same model on the raise size.

## Admin-console pricing controls (Kumar, 2026-11-26)

7. **The price book is edited in the admin console (T-072, Kumar only), not by deploy.** A pricing screen shows the current book — fixed fee, bps bands, variable cap, pilot flat rate — and edits create a **new book version with an effective time**; quotes bind to the version live at quote time, in-flight checkouts keep their quoted price, and already-collected prices never change. Every edit is audit-logged (who, when, before/after). Validation guards the obvious footguns: bands must ascend, bps within sane bounds, cap positive, and a version cannot be edited after it has quoted — corrections are a new version.
8. **Promo codes (pricing promotions), managed in the same console screen:** create codes (single or bulk for a campaign) with: discount kind — percent off the total, percent off the fixed fee, fixed amount off, variable waived, or pilot-flat override; validity window; redemption limits (total and per org); scope (any deal, pilot only, or named orgs). Redemptions are tracked per code and reported in the console (uses, revenue forgone). A code can be disabled instantly; disabling never touches completed purchases.
9. **Two different codes, one checkout — keep them distinct:** T-093's reseller codes are *attribution* codes; this task's promo codes change *price*. Checkout presents two clearly labelled fields ("Partner code" and "Promo code"), validates each against its own registry, and itemizes the effects separately — a customer can arrive with both.
10. **Stacking rule (default):** a promo discount and the T-093 reseller 10% do **not** stack — checkout applies the single better discount and shows which one won; each promo carries a `stackable` flag Kumar can set when a campaign should combine. Commissions (T-093) accrue on the amount actually collected after all discounts — T-093's "revenue" definition extends to promo discounts with no other change.


## Across countries and currencies (Kumar, 2026-11-26)

11. **One price book per market currency.** The model runs identically in every target market, but the numbers live in per-currency books — USD, EUR, GBP, JPY, INR — each with its own fixed fee, bps bands, cap and pilot rate, denominated and rounded in that currency (a JPY book prices in whole yen per T-170's minor-unit rules; an INR book in round rupees). Local books carry locally sensible numbers, not a machine conversion of the US book.
12. **The variable is computed in the deal's own currency:** a €100M deal prices off the EUR book's bands on €100M; a ¥10B deal off the JPY book on ¥10B. The pact's currency (T-170) selects the book at quote time, and the quote, checkout and receipt are entirely in that currency via Stripe.
13. **The console edits every book:** the pricing screen has a market switcher; each book versions and audit-logs independently (section 7 applies per book). Seeding a new book may *suggest* a converted starting point from the USD book — with the rate and date shown — which Kumar edits and confirms; the system never derives or updates a local book by silent conversion (T-170's rule, applied to pricing).
14. **Promo codes are market-aware:** a code can be scoped to specific books/markets (a Japan launch code valid only on the JPY book) or global; percent promos work in any currency; fixed-amount promos are denominated in the book's currency they apply to. Redemption reporting breaks down by market.
15. **Reseller money follows the same map:** commissions accrue in the collected currency per T-093 Part 7, whichever book priced the deal.

- Quote tests at the band edges: $10M / $25M / $50M / $100M / $250M / $500M reproduce the worked totals exactly, cap included; pilot quotes flat $5,000 at every size.

## Acceptance

- A $100M pact quotes $32,500 itemized ($5,000 fixed + $27,500 variable) at checkout in Stripe test mode.
- Changing a bps value in the price book changes quotes with no deploy.
- In the console, Kumar edits the fixed fee, publishes a new version, and a fresh quote uses it while an in-flight checkout keeps its original quote; the audit log shows the change.
- A promo code for 20% off, applied alongside a reseller code at checkout, attributes the customer to the reseller, applies the better single discount, itemizes both effects, and accrues commission on the discounted collected amount.
- A ¥10B pact quotes from the JPY book in whole yen, and a JPY-scoped launch promo applies to it while a USD-scoped promo does not; the EUR book's version history is independent of the USD book's.
- docs/pricing-research.md records the adopted model.
