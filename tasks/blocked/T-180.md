## Why

- *"If we need to notify users via email and sms/whatsapp, we need their email and phone no in profile."*
- *"SMS cost money but WhatsApp, telegram does not and so we support that."*

**Today:**
- `users.email` is filled only for email-code sign-in. Auth0 and SSO users have no email on file, so T-145's notification emails skip them silently, as "no address".
- No phone or messaging handle is stored anywhere.
- There's no profile screen: Settings is organization settings plus the notification preferences page.

## What to build
### 1. A profile screen ("Your profile")
A per-person page under Settings, built from the approved patterns in `docs/ui-patterns.md`. It shows the name, the email, and the message channels below, each with its verified state.

### 2. An email for everyone
- **Auth0 and SSO sign-in:**
  - store the verified `email` claim on sign-in, but only when `email_verified` is true; check the claim names against the installed Auth0 types and Auth0's docs;
  - with no verified email, the profile asks for one and confirms it with a one-time code. Reuse the email-code machinery (`packages/db/src/login.ts`).
- **Changing the address:** confirmed by a code sent to the new address, with a notice sent to the old one. Audited.
- **Existing users:** a one-time banner, "Add your email so Pactlab can tell you when a pact needs you", until they do.

### 3. Telegram (free; the default phone channel)
- **Linking:** the person taps **Connect Telegram**. This opens `https://t.me/<bot>?start=<one-time token>` (10-minute expiry, single use). The bot receives `/start <token>`, and Pactlab stores the `chat_id` against the person.
  - No phone number is needed.
  - Disconnecting works from Pactlab, and from Telegram by blocking the bot or sending `/stop`.
- **Provider:** the Telegram Bot API, behind a connector seam with a fixture adapter. It's off by default and needs a bot token from @BotFather; Kumar's step goes in a runbook as a short script or checklist.
  - Webhook updates are verified with the secret-token header (`X-Telegram-Bot-Api-Secret-Token`).
  - Verify the API against core.telegram.org/bots/api before writing code. Invent nothing.

### 4. WhatsApp (opt-in; paid per message, so Kumar approves before it's switched on)
- **Cost:** Meta charges per business-initiated template message, and the rate varies by country. Check the current pricing on Meta's official WhatsApp Business Platform pricing page and record it in the runbook. Per CLAUDE.md it's a paid dependency, so Kumar's approval is recorded in this file before it's enabled anywhere.
- **The number:** entered in international format (E.164, with a country picker) and confirmed with a one-time code sent over WhatsApp itself. Explicit consent is recorded: the time, and the text shown.
- **Provider:** behind a connector seam with a fixture adapter; off by default.
  - Candidates: AWS End User Messaging Social, which carries WhatsApp and fits the AWS-first stack, or the Meta Cloud API directly. Verify both against official docs and record the choice in the ADR.
  - Templates need Meta approval. Business verification is Kumar's step and goes in the runbook.
- **STOP:** handled, and it stops all WhatsApp messages immediately. Audited.

### 5. SMS
Not built (Kumar: it costs money). Remove it from T-146.

## Rules
- **Contact details are personal data:**
  - never sent to a model, logged or put in a fixture;
  - shown only to the person themselves, plus the organization admin (masked, e.g. `+91 •••• ••12`);
  - every read of an unmasked value outside the person's own profile is audited.
- **Verify before use:** a channel can't be used until it's verified, and the verified state is server-side.
- **The same rule for every channel:** a message never shows on a lock screen with deal content. It's content-free with a link, as in T-146's rule.
- **Migrations:** expand-only. Telegram and WhatsApp links get their own table (`user_contact_channels`: kind, handle or chat_id, verified_at, consent text and time, revoked_at), with RLS by user and organization.
- **An ADR,** covering the channel choices and their costs.

## Acceptance
- An Auth0 user with a verified email claim gets notification emails; one without is asked, verifies by code, and then gets them.
- Telegram: connect via the deep link (fixture), receive a content-free test message, disconnect, and nothing more arrives.
- WhatsApp: off by default; enabled in a test with the fixture, it verifies the number by code, sends one template message, and STOP ends sends.
- RLS: a person can't read another person's channels; an admin sees masked values only, and the read is audited.
- Tests prove no contact detail reaches a model call, a log line or the AI gateway.

- **Tests:** assert the sender name and the prefix on every outgoing payload.

- **This task:** the Telegram bot profile (name, picture, description) and the WhatsApp Business profile (display name, logo, about). The email-verification emails already go through the branded sender, so reuse it.
