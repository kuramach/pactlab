# T-110 — Reports: executive portfolio report + detailed pact report, PDF, versioned snapshots
Model: opus
Engine: claude

**Lane:** core
**Context:** deep
**Touches:** web (Reports menu page, pact report action), api (report generation, read models over pacts/findings/valuation), PDF rendering, document storage (generated PDFs), audit log
**Needs:** nothing open. Reads existing state only — pacts, phases, findings, claims registers, valuation runs, proposed terms, post-close register. Kumar specified this on 2026-11-09: two report types, in the menu, PDF, versioned because deals move.

## Why

Two audiences asked for the same thing from opposite ends (Kumar, 2026-11-09):

1. A lead PE firm running several deals wants one **executive report across all its open pacts** — where does everything stand?
2. Anyone deep in one deal wants a **detailed report on that pact** — the complete, presentable record.

And because a deal moves, a report is a snapshot of a moment: reports are **versioned**, never silently regenerated over an old one.

## The two reports

### 1. Executive report — all open pacts for the account

Scope: every pact the generating user's organisation participates in, grouped by the org's role in the pact (buyer / seller / advisor), open pacts first, recently closed below. Per pact, one compact block:

- Target and pact name, pack, phase (Pre / Diligence / Close / Post-close) and stage
- Headline economics as that org may see them: asking price vs current priced position (from the active valuation run)
- Findings posture: counts of open drags / cushions / neutrals, and the top open drags by priced impact
- Blockers and next actions: open review-queue items, outstanding proposals awaiting response, overdue post-close obligations where applicable
- Last activity timestamp

Header roll-up for the whole account: number of open pacts by phase, aggregate value in diligence, aggregate priced drag exposure. Every figure in the roll-up must be traceable to a per-pact block below it — no orphan totals.

### 2. Detailed report — one pact

The complete record, sectioned like the product (Overview / Diligence / Valuation / Close):

- Cover: pact, parties (as visible to the generator's org), pack, phase, generated-at, report version, "data as of" stamp
- Evidence inventory: documents and connected sources, with intake status
- Findings: full list with direction, status (proposed / accepted / rejected), priced impact where applicable, and rationale for neutrals
- Claims register where the pack has one
- Valuation: the bridge, scenarios, and the active run — including the persona the run was priced under (T-105) when the generator's org is the buyer
- Terms: proposals made, their status, and the current agreed position
- Post-close register where the pact has closed
- Foresight summary where present

## Versioning (the point of the task)

- Every generation creates a **new immutable version**: sequential per scope (account executive report v1, v2, ...; each pact's detailed report v1, v2, ...). Regenerating never overwrites or mutates an earlier version; the stored PDF bytes of a version never change after creation.
- Each version records: generated-at timestamp, generated-by user, scope, and the state it captured — the valuation run id(s) included and a findings count — so two versions can be compared honestly and nobody mistakes an old PDF for the current state of the deal.
- The PDF itself carries the version and "data as of" stamp on its cover and in the footer of every page.
- A Reports history list shows every version with its metadata and a download action. Version-to-version diffing is explicitly NOT in this task.

## Confidentiality (hard requirement)

A report contains exactly what the generating user's organisation is entitled to see in the app — enforced in the report read model, not by hiding sections in the template:

- Buyer-confidential material (persona, persona-priced runs, the confirmed-value ledger) appears only in reports generated by the buyer org.
- A seller-side (or advisor-side) user generating a detailed report on the same pact gets their visible subset only; the snapshot tests from T-083 / T-106 are the pattern: generated PDFs are tested to contain no counterparty-confidential content.
- The executive report includes only pacts the generator's org participates in, each rendered from that org's viewpoint.
- Report generation is audit-logged: who generated which report, which version, when. Reports are exports of sensitive deal data; treat them with the same care as the data itself.

## Product surface

- A top-level **Reports** entry in the app menu: choose executive (account) or pick a pact for a detailed report; the history list lives on the same page.
- A **Report** action on the pact itself that starts a detailed report for that pact and lands in the same history.
- Generation runs as a background job with a visible generating -> ready state in the history list; the PDF is stored alongside the pact/account documents.
- PDF rendering uses the locked brand (B2 logo, navy/indigo, Manrope), paginated, with real tables — a document a partner can forward, not a screenshot of the app.

## Explicit non-goals (v1)

- Scheduled or emailed reports; cross-version diffs; per-firm custom templates or branding; Excel/CSV export; any editing of a generated report.

## Acceptance

- Executive report for a seeded multi-pact account (demo org with pacts in several phases): roll-up figures equal the sum of the per-pact blocks; every open pact appears, grouped by the org's role.
- Detailed report on a demo pact reproduces its findings, bridge and terms faithfully against the in-app state at generation time.
- Generate twice with a deal change in between: v1's stored PDF is byte-identical before and after v2 exists; v2 reflects the change; both list correctly in history with their stamps.
- Confidentiality tests: a seller-generated detailed report contains no persona, no buyer-priced run and no confirmed-value content (text-extract the PDF and assert); an executive report contains no pact the generator's org does not participate in.
- Audit log records each generation.
