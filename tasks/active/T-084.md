# T-084 — Pactlab MCP server: the deal room inside the client's AI tools (plus MCP client mode for long-tail evidence)
Engine: claude

**Lane:** platform
**Context:** deep
**Touches:** api, domain, infra, spec
**Needs:** none — rides the existing REST API and services; no new business logic

## Kumar's ask (2026-10-26)

"Can Pactlab benefit from an MCP server and what could be the features for it?" — verdict delivered and approved the same day: yes. Deal teams work inside Claude/Copilot/etc.; Pactlab is already API-first with a typed evidence -> findings -> valuation model and a hard confidentiality boundary, so an MCP server is a thin channel over what exists — build the channel, reuse the machinery. This task is that build, in three parts: server mode (read), server mode (proposals), client mode (evidence intake).

## Design rule (read first)

The MCP layer contains **no business logic**. Every tool calls the same application services the REST API calls. If a capability doesn't exist as a service, it is out of scope for this task — file a separate task rather than growing logic inside the MCP adapter. This keeps one source of truth for valuation math, direction mapping, and confidentiality.

## Part 1 — Server mode, read-only (the core deliverable)

- A remote MCP server (streamable HTTP transport; no stdio — this is a hosted SaaS surface) co-deployed with the API, exposing org-scoped tools:
  - `list_deals` / `get_deal_summary` — phase (T-071), stage, screening verdict, key dates.
  - `get_findings` — filter by direction (-1/0/+1), severity, module/pack; returns the finding with its evidence links and rationale.
  - `get_claims_register` — claims with VERIFIED / CONTRADICTED / UNVERIFIED status and their linked findings.
  - `get_valuation_bridge` — the current bridge (base, adjustments, confirmed-value position shown separately, never merged into price).
  - `run_valuation_scenario` — ephemeral what-if: caller overrides named assumptions, server returns the resulting bridge. **Nothing persists**; a scenario is a computation, not a write.
  - `search_evidence` — search across the deal's normalized evidence and documents; returns citations (document, page/section) the client can quote.
  - `get_post_close_register` — asset-preservation and post-close action registers (T-071 Post phase).
  - `get_foresight` — the deal's trend lines and 5-year value path with assumptions and sensitivity ranking (T-073), returned as the range + assumptions, never a bare number.
- **Prompts** (packaged workflows, shipped with the server): "Screen this deal" (Pre-phase GO/NO_GO read), "Prep me for IC" (findings + bridge + open claims, ordered by materiality), "What will the investor find?" (Venture Raise founder self-diligence — the -1 register in investor-discovery order).
- **Auth:** OAuth 2.1 protected-resource flow per the MCP authorization spec, backed by the existing Auth0 tenants; the org comes from the token's org claim exactly as the API resolves it (T-010). Per-tool scopes: `mcp:read` baseline; confidential scopes below. A token never crosses orgs, and every tool enforces org + deal membership server-side — the client is untrusted.
- **Confidentiality in the tool layer (hard requirement, tested):** the confirmed-value ledger and founder-confidential findings (T-083) require an explicit confidential scope AND the matching party role. An investor-scoped principal on a Venture Raise pact can call the investor-facing tools and **cannot** reach founder-confidential data through any tool, filter, or search — `search_evidence` included. Direction-map semantics hold: +1 cushion content never appears in a counterparty-facing result set.
- **Audit:** every tool call writes to the existing audit log (T-072) — principal, org, MCP client identity, tool, deal, scope used, timestamp. Payloads and deal content are never written to application logs.
- Rate limits + payload caps sized to interactive use; large result sets paginate.

## Part 2 — Server mode, proposal tools (no silent writes)

- `propose_term` — from a -1 finding, draft a term proposal (PRICE_REDUCTION / REMEDIATION_COST / ESCROW / INDEMNITY) into the deal's proposal queue. It lands as a **draft requiring in-app human approval**; the MCP caller can read its status, never approve it.
- `draft_document_requests` — generate the counterparty document-request list from open evidence gaps (Pre/Diligence phases); draft only, same approval rule.
- `export_counterparty_view` — produce the investor-facing (Venture Raise) or seller-facing share artifact from the current deal state, honoring the Part 1 confidentiality boundary; the export itself is an audited event.
- `submit_evidence` — an external agent may submit candidate evidence; it enters as unnormalized input and passes the standard pipeline, including `VALUATION_DIRECTION_MAP` registration checks (contract test applies). Unmapped types are rejected with the reason, never silently dropped.

## Part 3 — Client mode: MCP servers as evidence sources (bounded spike)

- Pactlab can also *consume* MCP: an operator-configured external MCP server (customer's internal tools — e.g. Notion/Linear/HubSpot-class systems that already ship servers) registers as an evidence source under the connector framework.
- Scope discipline: operator allowlist only (configured by Kumar/admin, never a user-typed URL at runtime — same SSRF posture as T-082's Jira allowlist); read-only; outputs normalized into evidence through the existing pipeline with direction-map registration required before any finding can result.
- Deliverable is one working source end-to-end (developer's choice of a mainstream reference server) + the registration pattern documented; the long tail follows the pattern, not this task.

## Guardrails

- Read-only by default; every write-shaped tool produces a draft/proposal for human approval. Nothing an AI client does through MCP can change price, terms, or shared artifacts on its own — that is the brand ("AI rigor. Human judgment.") enforced as protocol.
- No deal content in logs, no payload logging, no cross-org leakage — each with a test.
- Per-environment rollout matches T-070: dev first; the server ships dark (feature flag per org, via the T-072 admin toggles) until Kumar enables it per org.

## Acceptance

- From a standard MCP client (Claude desktop/app is the reference), a user with an org token can list their deals and pull summary, findings (direction filter works), claims register, and bridge for a demo pact (HealthyCo); an ephemeral scenario returns a changed bridge and persists nothing (verified).
- A token from a second org gets nothing from the first org's deals on any tool, including search (tested).
- On a Venture Raise demo pact, an investor-scoped principal receives zero founder-confidential findings across all tools and search (tested); the confirmed-value ledger requires the confidential scope (tested).
- `propose_term` creates an approvable draft in-app and cannot be approved via MCP (tested); every tool call appears in the audit log with client identity (visible in the T-072 console).
- Client mode: one allowlisted external MCP server connected as an evidence source; its output normalizes into evidence and cannot produce a finding until its evidence type is in VALUATION_DIRECTION_MAP.
- Server deploys behind the per-org feature flag, off by default; docs page covers client setup (Claude/Copilot) and the scope model.
