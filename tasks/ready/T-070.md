# T-070 — Skinny QA, stage, and prod environments for client showcases

**Lane:** infra
**Context:** deep
**Touches:** infra, docs
**Needs:** Kumar (AWS member-account creation + explicit per-env deploy go; Auth0 production-tenant setup — both are dashboard/account actions the agent must NOT do unprompted)

## Why

Kumar has only the AWS dev environment (member account 379959319207). He wants skinny QA, stage, and prod environments to showcase to clients BEFORE investing in redundancy and throughput. The CDK already synthesizes one stack per environment from typed config (`infra/cdk/config/`); this task makes qa/stage/prod actually provisionable at showcase cost, with the full-production profile deferred as config values to flip later.

## What exists (do not rebuild)

- `infra/cdk/bin/pactlab.ts` synthesizes `PactlabDev/Qa/Stage/Prod` + site + deploy-access; binds account via `-c pactlab:<env>:account=<id>`; fails closed when active credentials resolve to another account.
- `infra/cdk/config/qa.ts` is already skinny (t4g.medium, single-AZ, 20 GiB, 1 NAT, cache.t4g.micro x1, unprotected, seeded with HealthyCo/TroubledCo/SparseCo) — it is the size model for the other showcase envs.
- `infra/cdk/config/stage.ts` is currently "production shape at reduced capacity" (t4g.large, **Multi-AZ**, 2 NATs, protectedState true) — bigger than skinny; skinny it.
- `infra/cdk/config/prod.ts` is the FULL build (m7g.large, Multi-AZ, 3 AZ/3 NAT, cache.m7g.large x2, COMPLIANCE archive 2555 days) — this is the deferred "go big" profile. Keep every value documented; none of it ships now.
- `infra/cdk/lib/protection.ts`: the `protectedState` aspect fails synthesis when stateful protection is missing on stage/prod. Skinny must NOT mean unprotected — qa stays unprotected/resettable; stage and prod keep protectedState true.

## What to build

1. **Showcase sizing for stage and prod.** Give stage and prod qa-class sizing (t4g.medium or smaller DB, single-AZ, 1 NAT gateway, cache.t4g.micro x1; prod keeps backups ON and deletion protection ON). Parameterize so the deferred full profiles are config flips, not re-architecture: keep the current stage/prod values as named constants or in a documented "scaled target" section so going big later is a one-change diff. Protected-state enforcement must keep passing.
2. **Account wiring.** qa/stage/prod are member accounts in the PactLab-Team org (mgmt 042954450979). Follow the existing CLI-profile convention `pactlab-<env>` (dev already works this way) and extend the deploy-access OIDC pattern so each env has its own GitHub Actions deploy role. Account IDs travel as CDK context `pactlab:<env>:account` and are NEVER committed — same as today. **The agent creates NOTHING in AWS and runs NO deploy on its own:** this task's PR is config + synth + tests + runbook only. Provisioning each env happens later on Kumar's explicit per-env go.
3. **Auth0.** qa/stage ride the dev tenant (dev-08orcvlqtg3b2dd4) — T-010 is env-driven for exactly this; the runbook lists the exact callback/logout/origin URLs to register per env. **prod gets its own production tenant, never the dev tenant** — dashboard setup is Kumar's step (or paired), listed as a pre-deploy checklist item.
4. **Domains/TLS.** qa./stage./app.pactlab.ai (subdomains of pactlab.ai) with ACM certs in the deploy; document the DNS records Kumar must add at the registrar.
5. **Showcase data.** Seed qa (and stage/prod-showcase) with synthetic demo data only: the qa config's HealthyCo/TroubledCo/SparseCo model, and the per-pack synthetic generator (T-053) for pack showcases. Nothing real ever touches a client-facing env.
6. **Runbook.** `docs/infra/envs.md` (or the equivalent infra docs path): per-env account creation, CLI profiles, Auth0 registration checklist, seed/reset commands, qa teardown for cost control, estimated monthly cost per env at showcase sizing (always-on estimate ~$140/mo/env: NAT ~$34 + ALB ~$18 + RDS t4g.medium ~$50 + ElastiCache micro ~$9 + Fargate ~$27 + misc ~$5; qa/stage torn down between demos brings the three-env typical month to ~$180-250), and the one-change path to the scaled profile.

## Guardrails

- No AWS account creation, no `cdk deploy`, no Auth0 tenant changes from the agent. Code + docs only.
- Nothing about the user's money or accounts moves without Kumar's explicit word — this is a code task, not a provisioning task.
- Keep the four-environment shape, the env-driven app config, and the fails-closed account binding exactly as they are.

## Acceptance

- `cdk synth` succeeds for all four environments with the new showcase sizing; the `protectedState` aspect still enforces on stage/prod (a test proves a missing RETAIN/deletion-protection fails synthesis).
- A contract test pins qa/stage/prod to the skinny tier (t4g-class DB, single-AZ, single NAT) so a future edit can't silently scale them back up.
- Docs: runbook + cost band + scaled-target profile documented; pre-deploy checklist (accounts, Auth0 prod tenant, DNS) written as Kumar-gated steps.
