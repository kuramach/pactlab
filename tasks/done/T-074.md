## Kumar's ask (2026-10-24, main chat)

"I need a Github public repo for integration testing. Medium scale repo and also a public Jira repo" — targets for testing the GitHub and Jira integrations (evidence adapters). Kumar directed this task be created from the main-chat research on 2026-10-24.

## Decision: the Apache Kafka pair

Use one real open-source project that lives on BOTH systems, so cross-system linkage is testable, not just single-API reads:

- **GitHub:** `apache/kafka` — 34.1k stars, ~320 MB repo, ~670 open issues+PRs, 15.6k forks, steady PR and CI volume (verified 2026-10-24 via GitHub API). PR titles and commit messages carry Jira keys (`KAFKA-1234` style) — the realistic evidence-linkage shape for diligence.
- **Jira:** Apache's public instance, **issues.apache.org/jira**, project **KAFKA** — 20,064 issues (verified 2026-10-24). REST API answers **anonymously**: `GET /rest/api/2/project/KAFKA` and JQL search both returned data with no credentials. No account or token needed for read paths.
- **Secondary Jira (contrast/fallback):** `jira.atlassian.com` (project JRASERVER) — also verified anonymous-readable 2026-10-24. Different hosting flavor (Atlassian's own) vs Apache's self-hosted instance; useful to catch base-URL/field assumptions.

Alternates considered, do not use unless Kafka sync cost bites: `encode/django-rest-framework` (30k stars but only ~66 MB / 63 open items, no Jira pairing, low PR churn) and `grafana/loki` (565 MB, ~1,184 open items, GitHub-issues only, no Jira).

## Scope

1. **GitHub adapter tests** against `apache/kafka`: repo metadata, PR list/detail, reviews, check runs / CI status, commits. Pagination at medium scale; rate-limit behavior authenticated (existing connector token) vs unauthenticated; extraction of `KAFKA-\d+` keys from PR titles and commit messages.
2. **Jira adapter tests** against issues.apache.org/jira project KAFKA: project metadata, JQL search, issue detail (comments, status transitions / changelog, attachment metadata). Pagination across a 20k-issue project; anonymous-access path plus the authenticated path.
3. **Cross-link test (the point of the pair):** given a Kafka PR referencing `KAFKA-xxxx`, resolve to the Jira issue; given a Jira issue, find referencing PRs by key scan. Assert both directions on a small fixed sample.
4. **Hermetic by default:** record fixtures from these targets for unit tests. Live smoke tests run only behind an env flag (e.g. `INTEGRATION_LIVE=1`), nightly or manual — never in the PR gate.

## Known limits (accepted)

- Both targets are **read-only** for us: no write paths (create issue / open PR) and no webhook-delivery testing. If write testing is needed later, create an owned public repo + a free Jira Cloud site as a second pair — that creation needs Kumar's explicit go (asked 2026-10-24, no decision yet).
- Public instances change under us (issues close, PRs merge): live tests must assert shapes and invariants, not exact counts.
