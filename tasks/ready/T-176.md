**Needs note:** intake is T-175's chat (the confirm-and-hand-off hook); the store, triage and task conversion here are built against that contract.

## Why

Kumar (2026-11-26): when a user asks for a new feature through the chat, it gets logged as a task for us to approve or reject. This task is that pipeline — the same discipline as the log-triage flow (T-150): nothing becomes a build task without Kumar's explicit approval, and the person who asked can see what happened to their request.

## Build

1. **Proposal store:** a feature request becomes a proposal record — the requester's own wording (title + description as confirmed in chat), source surface (site/app), locale, page context, and the conversation excerpt that led to it. In-app requests carry the user and org; public-site requests carry the email the visitor gave for follow-up (required — anonymous drive-by requests are not stored). Rate limits and a spam screen on the public intake.
2. **Dedupe and grouping:** near-duplicate requests group under one proposal with a supporter count (each additional requester attached, not a new proposal), so triage sees demand, not noise. Grouping is suggested by similarity and confirmed by the triager — never auto-merged silently.
3. **Admin triage (T-072 console, Kumar only):** the queue lists proposals with source, supporters and context; actions: **approve**, **reject** (with an optional short reason), **request info** (emails the requester a question; their reply reopens the proposal). Approval converts the proposal into a house-format task file in `tasks/ready/` (Engine/Model/Lane/Context/Touches/Needs headers; tier and touches proposed from the proposal's surface, editable by Kumar before the file is written) through the same GitHub machinery pattern as T-150's triage-to-task flow — the task records its origin proposal id, and the proposal links to the task and its eventual PR.
4. **Requester visibility:** in-app users see their requests and statuses (submitted → in triage → approved/planned → declined, and once built, shipped with the What's-new card link). Public-site requesters get the status changes by email. Status language is honest: "approved" means a task exists, not a date.
5. **Guardrails:** no proposal becomes a task without the admin approval action — the chat cannot create tasks; rejected proposals are retained (searchable, so a repeat request resurfaces the earlier decision and its reason); proposal content is product-feedback only and never contains pact data (T-175's boundary guarantees the intake).

## Checks

- End-to-end test: chat-confirmed request → proposal → approve → task file exists in tasks/ready/ with origin id → requester status shows approved; reject path shows the reason.
- Dedupe test: a second similar request attaches as a supporter instead of a new proposal.
- Permission tests: the queue and actions are admin-only; a requester sees only their own requests.

## Acceptance

- Kumar can open the admin queue, approve a real proposal, and find the generated task in the repo; the requester sees the status change without being told a date.
- A declined request with a reason resurfaces, reason attached, when someone asks for the same thing again.
