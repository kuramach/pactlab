# T-072 — Admin console and in-app bug reporting (one build)

**Lane:** core
**Context:** deep
**Touches:** domain, db, api, web, ops
**Needs:** none

## Why (Kumar, 2026-10-23)

Two operator/user gaps: (1) there is no admin page — org sign-up approvals are CLI commands (`pnpm org:pending / org:approve / org:reject` in `apps/api/src/ops/`); (2) users have no way to report a bug in-app. Kumar asked for both as ONE task, and specifically asked whether the app can **screen-capture at the moment a bug happens** — yes, for the in-app view (see Part B; browsers make silent full-desktop capture impossible by design, so the scope is the Pactlab view itself, which is where the useful context is).

## Scope decisions (from the 2026-10-23 discussion)

- **Platform admin only** (the operator = Kumar), not customer org-admin self-service. Org admins keep managing their own deal members as today.
- **Metadata only.** The console never exposes customer deal content (no evidence/findings/valuation bodies). Counts, statuses, and IDs only. No impersonation / "view as user" — deferred deliberately, do not build it.
- Screenshot capture is IN (auto on error + on manual report). Convert-to-task is IN as an export (see Part B).

## Part A — Admin console (`/admin`, operators only)

Access: a platform-operator flag on the user record, settable initially via the existing ops CLI; every `/admin` API route rejects non-operators (403) and every admin action is audit-logged with actor, action, and target.

1. **Approvals queue.** Pending org sign-ups with approve/reject in UI, reusing the existing `ops/organizations` service functions (`listPending` / `decide`) — the CLI stays as a fallback, the logic is not forked. Show the SSO-requested flag.
2. **Organizations.** List with status and owner; suspend / reactivate; per-org feature flags (**pilotMode**, **liveConnectors**) as toggles writing through the existing SSM flag publishing — no deploys to change a flag.
3. **Users.** Per-org member list with roles; deactivate a user; cross-org search by email/name.
4. **Usage & health.** Per org: deal count by phase, member count; platform: Bedrock token usage/cost rollup, connector sync status per connection (last sync, last error), app version + environment banner so the operator always knows which env the console is looking at.
5. **Audit log viewer.** Platform-scoped events (approvals, flag changes, suspensions, bug triage) with filters by actor/action/date.
6. **Bug inbox.** Part B's triage queue lives here (list, filters by status/severity/org/env, detail view, status + internal notes).

## Part B — Bug reporting (in-app)

**Report flow.** A "Report a bug" entry in the app chrome opens a modal: title, what happened, what was expected, severity (Low / Medium / High / Blocker). Auto-attached without the user typing any of it: route/URL, app version + build, browser UA, org ID, deal ID when in a deal, user ID, environment, timestamp.

**Screen capture (Kumar's ask).**
- *On error:* a global handler (React error boundary + `window.onerror` / `unhandledrejection` + surfaced API failures) catches an unhandled error, immediately renders a **screenshot of the current in-app view** (DOM-to-image render of the app root) and stashes the error detail (message, stack, failing request, recent console errors). A non-blocking prompt appears: "Something went wrong — send a bug report?" with the screenshot and context already attached; the user adds a line if they want and sends, or dismisses.
- *On manual report:* the modal generates the same current-view screenshot on open (user can remove it).
- *Privacy rules (hard requirements):* capture is the app's own DOM only — never other tabs or the desktop (`getDisplayMedia` is out: the browser forces a permission prompt every time, so it cannot be automatic). Mask password inputs and any element marked `data-private` in the render. Cap image dimensions/bytes; store as an object with a signed URL, same pattern as evidence files.

**Storage & lifecycle.** `bug_reports` table: reporter, org, context JSON, screenshot reference, severity, status (`NEW, TRIAGED, IN_PROGRESS, RESOLVED, WONT_FIX`), plus operator-only internal notes. RLS: a reporter sees only their own reports; operators see all (metadata + the report itself — a bug report is user-submitted content, not deal content). Reporters get a "My reports" list with live status.

**Convert to task.** From the inbox, one click exports a confirmed bug as a T-style markdown file (title, repro from the report, context block, screenshot link) via copy/download — the operator drops it into `tasks/ready/` and the loop picks it up. Do NOT put GitHub credentials inside the app for this; direct repo push is a later option if the export proves clumsy.

## Acceptance

- Non-operator hitting any `/admin` route or API gets 403; admin actions appear in the audit log.
- Approvals: a pending org approved in the UI activates the same way the CLI does (shared service, existing ops tests still green).
- Flag toggle in the console changes the org's effective flags without a deploy.
- Triggering a test error in the web app produces the prompt with a masked screenshot attached; submitting creates a report visible in the admin inbox and in the reporter's "My reports"; a status change in the inbox reflects to the reporter.
- Screenshot masking is covered by a test (a `data-private` element and a password field do not appear in the captured image).
- Convert-to-task export produces a markdown file containing title, description, severity, context, and screenshot link.
