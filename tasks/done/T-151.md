# T-151 — Semi-automated daily tester plan: generated plans, bug intake, retest loop

Engine: claude
Model: sonnet
Lane: platform
Context: standard
Touches: docs scripts .github tasks
Needs: none

## Why

Kumar is hiring a human tester (2026-11-24). The tester needs a fresh plan every day, generated from what actually changed — not a static checklist repeated by rote. Kumar approved the system design on 2026-11-24: each morning's plan is assembled from yesterday's merges and deploys, a weekly rotation across packs and core surfaces, the open-bug retest list, and (once T-150 lands) the live-error triage digest. Bugs come back as GitHub issues in a fixed template; Kumar triages; approved bugs become tasks. This task builds that machinery in the repo.

## Build

1. **Plan generator** (a script under scripts/, builder's choice of shell or node, consistent with repo tooling): assembles today's plan markdown from —
   - merges to main since the last generated plan (a watermark kept beside the generated plans), each merge becoming a concrete regression check in the "what changed" section;
   - the weekly rotation table (below) for the day's focus area;
   - open GitHub issues labelled `tester-bug` whose fixes have merged (the retest section);
   - the latest T-150 triage digest, when one exists (its top clusters become exploratory charter suggestions).
   Output: `docs/testing/plans/YYYY-MM-DD.md`, filled from the daily plan template.
2. **Templates** under `docs/testing/`: the daily plan (smoke first, then regression-from-changes, rotation focus, exploratory charters, retests — with timeboxes and exit criteria), the end-of-day report, and the week-1 tester onboarding checklist. Plus a GitHub issue template at `.github/ISSUE_TEMPLATE/tester-bug.yml` carrying the bug format (env/build, account/org/pact, steps, expected vs actual, evidence, frequency) and the severity scale: S1 blocker or confidentiality leak, S2 major/wrong result, S3 minor with workaround, S4 cosmetic.
3. **System doc** `docs/testing/tester-plan-system.md`: the rotation (Mon core platform; Tue pack deep-dive A; Wed money path — bridge, personas, confidentiality walls; Thu pack deep-dive B + integrations; Fri retest sweep + cross-browser/mobile + free-range charter), the pack rotation order (software-saas, healthcare, small-clinics, hospitals, fintech, ecommerce-dtc, commercial-property, multifamily, hotels, pharma-biotech, professional-services, telecom-media, venture-raise; unbuilt packs join when they merge), and the ground rules: new work tested on dev; live gets prod-safe checks only, inside demo orgs; Stripe test mode and BoldSign sandbox recipients only; the tester never re-walks a path the Playwright suite already covers green — smoke runs first, humans hunt what automation can't see.
4. **Triage hand-off, documented not automated:** the system doc states the approval flow — Kumar triages `tester-bug` issues; approved bugs are filed as task files (the T-150 `triage-approved` pattern may be reused later; building auto-task creation is out of scope here).

## Guardrails

- The generator reads git and GitHub state only and writes only the generated plan file. No application code changes.
- Plans and templates contain no secrets and no real customer data (none exists); demo identities only.
- The smoke-first rule is structural in the template, not a suggestion.

## Checks

- Run the generator against the real repo: today's plan appears in `docs/testing/plans/` and its "what changed" section lists actual recent merges.
- Issue template is valid YAML and appears in GitHub's new-issue chooser.
- Repo lint/test suite green.

## Acceptance

- One command produces a complete, dated daily plan a tester can execute without further briefing.
- A bug filed through the issue template carries every field Kumar needs to triage it.
- The system doc lets a new tester run their first week from the onboarding checklist alone.
