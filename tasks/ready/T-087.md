# T-087 — Pricing and Stripe: subscriptions, per-pact purchase, and entitlements so Pactlab can collect money

**Lane:** platform
**Context:** deep
**Touches:** api, domain, web, admin, infra, spec
**Needs:** none to build in Stripe **test mode**. Going live is gated (Part 4): Kumar supplies live keys via env at go-live and gives the explicit go — the loop never flips to live money on its own.

## Kumar's ask (2026-10-26)

"A new task for pricing and Stripe integration so we can collect money."

## Part 1 — The pricing model (structure now, numbers are Kumar's)

The engine must support the model without code changes when prices change — **prices are data** (a pricing table: Stripe price IDs + display config), never literals in code.

- **Per-pact purchase (the core unit):** diligence is episodic and deal-sized — a buyer runs a pact when there's a deal, and the fee is trivial against the transaction. One payment buys one pact, full modules for that deal, no seat math. This is the default way to buy.
- **Firm subscription (the repeat buyer):** advisory firms / serial acquirers running many pacts: an annual org subscription covering a pact allowance (with per-pact overage at the standard rate) plus multi-seat access. Same engine, different price-book row.
- **Venture Raise (founder side):** same engine, founder-priced row — founders are price-sensitive in the opposite direction; the row exists in the price book, Kumar sets its number.
- **Pilot/free:** unchanged — `pilotMode` orgs (T-072 flag) run free and never see a paywall. Trials for paying plans, if any, are Stripe trial config, not special code.
- **Price points: Kumar's decision.** The task builds with placeholder prices in test mode; the price book ships as a config table whose real values Kumar sets before go-live. No price is invented by the build. (Context for his decision, from the standing competitor notes: valuation-only tools charge ~$1,595/seat; Pactlab sells the whole loop, per deal.)

## Part 2 — Stripe integration (hosted surfaces — best-in-class rule)

- **Stripe Checkout** for all payments (per-pact one-time, subscription start). Card data never touches Pactlab servers — PCI scope stays at the minimum (SAQ-A posture).
- **Stripe Billing** for subscriptions + **Stripe Customer Portal** (hosted) for invoices, card updates, plan changes, cancellation. We build **no** billing UI of our own beyond entry points and status display.
- **Invoice payments** for firm plans: Stripe Invoicing enabled so firms can pay by invoice/wire on annual plans (advisors run on POs; cards alone would block the segment).
- **Webhooks (the actual integration):** a signature-verified endpoint handling checkout completion, invoice paid/failed, subscription created/updated/canceled, payment failure. Handlers are **idempotent** (event-ID dedupe; replay-safe) — an entitlement is granted or revoked only from a verified Stripe event, never from a browser redirect.
- **Stripe is the source of truth for money.** The app mirrors billing state (customer ID, subscription status, current period, pact credits) for entitlement checks and display; a nightly reconciliation job re-syncs mirrors from Stripe, and the admin console has a manual resync per org.
- **Tax:** Stripe Tax evaluated in the build and set per Kumar/CPA direction (SaaS taxability is jurisdiction-dependent); the config flag exists either way. Not silently skipped, not silently enabled.
- Secrets (API keys, webhook signing secret) live in env/SSM per environment — never in the repo, never logged.

## Part 3 — Entitlements and app surfaces

- **Entitlement model:** an org can run a pact if it has (a) an active subscription with allowance remaining, (b) an unused per-pact credit, or (c) pilotMode. Creating a pact consumes allowance/credit at pact creation (not at first finding), and the consumption is visible and auditable.
- **Access states** mapped from Stripe: active -> full; past_due -> grace (existing pacts readable + completable, no new pacts, banner showing why) for a configured window; canceled/unpaid -> read-only archive access (a customer's diligence record is never held hostage or deleted for non-payment — they just can't run new work).
- **In-app surfaces (minimal):** current plan + status + pact credits on the org settings page; "Buy a pact" / "Upgrade" entry points that hand off to Checkout; billing link that hands off to the Customer Portal.
- **Admin (T-072 console):** per-org billing status (plan, Stripe status, credits, period end) read from the mirror, with resync; admins can comp a pact credit (audited) — support needs this on day one.
- Every money-relevant event (grant, consume, comp, revoke) goes to the audit log.

## Part 4 — Money safety and go-live gate

- Build and acceptance run **entirely in Stripe test mode** with test clocks (subscription lifecycle simulated, not waited on).
- **Go-live checklist** (in the PR/runbook): live keys installed via env, webhook endpoint registered for live mode, price book filled with Kumar's real values, tax flag set, one real low-value transaction run and refunded as the smoke test. Each step is Kumar's explicit go — the default state of this task's output is *capable of charging, not charging*.

## Guardrails

- No card data on our servers, ever; no payment secrets in code/logs/chat.
- No entitlement without a verified paid event; no double-grant under webhook retries/replays (tested).
- A billing outage or Stripe downtime never locks a paying customer out of existing pacts: entitlement checks fail open for reads on existing work, closed only for new-pact creation, and the state self-heals on reconciliation.

## Acceptance (all in test mode)

- Buy-a-pact flow: Checkout completes -> webhook grants exactly one credit -> pact creation consumes it -> second pact creation is blocked with a clear buy path. Replaying the webhook grants nothing extra.
- Subscription flow: subscribe -> allowance available -> Customer Portal cancel -> access continues to period end -> then read-only archive state. Failed payment -> past_due grace behavior as spec'd.
- pilotMode org: no paywall anywhere, no Stripe customer required.
- Admin console shows an org's billing status and a comped credit lands with an audit entry.
- Reconciliation job corrects a deliberately corrupted mirror row from Stripe.
- Runbook documents the go-live checklist; production remains in test mode until Kumar runs it.
