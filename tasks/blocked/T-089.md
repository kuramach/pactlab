# T-089 — Redline flow: Word tracked changes and comments as pact evidence, in every pact
Status: postponed by Kumar (2026-10-29). The slice 1 plan is below; move back to tasks/ready/ to resume.
Engine: claude

**Lane:** platform
**Context:** deep
**Touches:** domain, connectors (document pipeline), web, packs, spec
**Needs:** none — extends the existing document pipeline (T-076 viewer, T-077 document findings)

## Kumar's ask (2026-10-26)

"Lots of deals use MS Word and redlines to agree and disagree. How do we integrate that flow into all the pacts?" — design approved the same day: **don't build an editor; make the redline a data source.** Counsel keeps working in Word; Pactlab parses every round into the pact's evidence, findings, and valuation machinery. Core platform module — every pact produces Word documents, so this is not a pack feature; packs add document types to it (Part 5).

## Part 1 — Redline ingestion (parse, never convert-and-hope)

- Upload a .docx round into the pact's documents; the parser reads the OOXML directly and extracts **tracked insertions, deletions, moves, and format changes**, plus **margin comments** (author, timestamp, anchored text, thread/reply structure) as structured records. Nothing is flattened to plain text first — the revision structure is the evidence.
- Every extracted change/comment becomes normalized evidence in the existing pipeline (source: document + round + author), so it flows to findings under `VALUATION_DIRECTION_MAP` like any other evidence type (new evidence types registered here, contract test applies).
- **Fidelity rule:** the original file is preserved byte-for-byte and remains the legal artifact; parsed records always cite back to it. Any revision construct the parser doesn't understand is surfaced as unparsed-with-location, never silently dropped.

## Part 2 — Version chain, redline register, compare

- **Version chain per document:** rounds in order (v1 our draft -> v2 their redline -> ...), each labeled with side/author org, timestamp, and who holds the next turn. "Ball with seller's counsel since Tuesday" is computed from the chain, not typed by someone.
- **Redline register:** every change and comment across all rounds with status — proposed / accepted / rejected / superseded / open — carried forward automatically: a change not present in the next round is marked how it resolved (accepted into text, dropped, or still contested in altered form — matching is by anchored text + author intent, with ambiguous matches flagged for a human, never guessed silently).
- **Compare view:** side-by-side diff between any two rounds, reusing the T-076 viewer pattern; comments shown in place with their resolution state, including comments the counterparty deleted (deletion is itself a negotiation signal and stays in the register).

## Part 3 — Economic mapping and the round digest

- **Economic-change detection:** changes touching priced terms — purchase price mechanics, escrow/holdback %, caps and baskets, survival periods, working-capital and EBITDA definitions, earnout metrics, closing conditions — are detected (defined-term + number-change analysis against the document's defined terms) and raised as findings linked to the valuation bridge and, where the term model covers the term, **priced**: "Round 3 cuts escrow 10% -> 7.5%: bridge impact shown." Where the model doesn't cover it, the finding is flagged for human pricing — never silently priced, never silently ignored.
- **Claims cross-flag:** a redline that strikes or weakens language a claim depends on (e.g., a rep that diligence evidence has CONTRADICTED) cross-flags in the claims register automatically.
- **Round digest:** each new round produces a plain-language digest — what changed, grouped as economic / risk-shifting / drafting, with the material items first — every line citing the specific parsed changes it summarizes. The digest is a view over the register, not a free-floating summary.

## Part 4 — Round-trip and the executed set

- **Export:** at any point, export the document as (a) clean .docx (all accepted state applied) or (b) marked .docx reflecting the current register state, so counsel continues in Word without re-keying. Export fidelity is tested by re-parsing the export (round-trip test).
- **Executed set -> Post-Close (T-071):** when a document is marked executed/final, its final text becomes canonical for that document, and time-bound obligations in the agreed text — escrow release dates, earnout milestones and measurement dates, survival/expiry deadlines, notice windows — are extracted into the post-close action register. Post-close tracks what was actually agreed, not what the first draft proposed.

## Part 5 — All pacts: document-type registry + the Venture Raise flip

- **Document-type registry per pack:** the core module ships with the generic deal set (LOI, term sheet, purchase agreement, disclosure schedules, NDA). Packs register their types (hotels: franchise agreement + PIP exhibit; hospitals: medical staff / payer exhibits; etc.) — types drive which defined-term/economic patterns Part 3 watches for. Adding a type is configuration + patterns, not new machinery.
- **Venture Raise (T-083):** the same engine reads a VC's redlined term sheet/SAFE: changes to valuation cap, discount, pool %, pro-rata, board seats, and liquidation terms map directly into T-083's term model and show the founder the dilution/term impact per change. Buyer-side SPA redlines and founder-side term-sheet redlines are one flow with two term models.

## Explicitly out of scope

- No in-browser Word editor, no co-editing, no e-signature (integrate a signing provider later if ever). No .doc (legacy binary) support — .docx only, legacy files are asked to be saved as .docx.
- Microsoft Graph / OneDrive / SharePoint sync (where firm documents live) is a **phase-2 connector**, designed-for here (the ingestion API takes a document + round metadata regardless of source) but not built in this task.

## Guardrails

- Originals are immutable and access-controlled exactly as the pact's other documents; parsed redline data inherits the pact's confidentiality (incl. the T-083/T-084 counterparty boundaries — a seller never sees the buyer's internal register annotations).
- Internal annotations on the register (our read of their moves) are a separate layer from the document record and are never included in exports.
- Parser handles hostile/odd files defensively (zip bombs, malformed XML) under the import pipeline's existing limits.

## Acceptance

- Fixture set (authored at OOXML level): a purchase-agreement excerpt across 3 rounds with tracked changes + threaded comments, and a redlined VC term sheet. Parser extracts 100% of planted changes/comments with correct author/round/status; the one deliberately exotic construct surfaces as unparsed-with-location.
- Register carries statuses across rounds correctly, incl. a deleted comment remaining visible as deleted; next-turn holder computed correctly at each round.
- The planted escrow change produces a priced bridge impact; the planted definition change produces a flagged-for-human-pricing finding; a struck rep tied to a CONTRADICTED claim cross-flags.
- Round digest covers every material planted change with citations and invents none.
- Export round-trip: exported marked .docx re-parses to the same register state; executed-set extraction lands the planted escrow-release and earnout dates in the post-close register.
- Term-sheet fixture: cap + pool changes show founder dilution impact via the T-083 model.

### Approach

#### 1. OOXML redline parser (pure, defensive)

New `packages/connectors/src/redline/`:

**`parse.ts` — `parseRedline(bytes) → RedlineParse`**
- Unzip with `fflate` (already a dependency), using the archive limits pattern from `apps/api/src/documents/archive.ts`: entry count, expanded-size cap, and only the parts we need (`word/document.xml`, `comments.xml`, `commentsExtended.xml`).
- A small streaming XML tokenizer of our own, rather than a new dependency:
  - refuses `<!DOCTYPE`/entities, which blocks XXE and billion-laughs;
  - caps depth and token count;
  - decodes only the five XML escapes and numeric refs.

**What it extracts**
- Paragraphs in body order, keeping both the accepted text and the original text.
- Changes: `w:ins`, `w:del` (`w:delText`), `w:moveFrom` / `w:moveTo` (paired by the move range name), and `w:rPrChange` / `w:pPrChange` (format). Each carries:
  - Word revision id, author, date, kind;
  - the text;
  - paragraph index and paragraph context (anchor text).
- Comments from `comments.xml`: id, author, date, text, and anchored text from `commentRangeStart`/`End`.
- Comment threading and the done flag from `commentsExtended.xml`, via `w15:paraIdParent`.
- **Unparsed constructs:** any other revision-markup element is reported as `{element, part, paragraphIndex}` instead of being dropped. Examples: `w:cellIns`, `w:cellDel`, `w:tblPrChange`, `w:sectPrChange`, `w:numberingChange`, `customXml*Range`.

**`fixtures.ts` — `buildDocx(spec)`**
- Writes OOXML parts directly and zips them with `fflate.zipSync`, so the fixtures are authored at OOXML level as the acceptance criteria require.
- Ships the acceptance fixtures:
  - **Purchase agreement, 3 rounds** (buyer v1 → seller v2 → buyer v3). Planted items:
    - escrow 10% → 7.5% (insertion + deletion);
    - a definition change;
    - a struck rep;
    - a moved clause;
    - a format change;
    - a threaded comment, and a comment the counterparty deletes in v3;
    - one exotic `w:cellIns`.
  - **VC term sheet** (cap and pool changes), parsed only in this slice. It is used in slice 4.
- A script writes these to `fixtures/synthetic/redlines/*.docx` for demo use.

**Evidence types and direction rules**
- Two new evidence types: `redline.change` and `redline.comment`.
- Both get INFORMATIONAL rules in `VALUATION_DIRECTION_MAP`, with a rationale, and join `ADAPTER_EVIDENCE_TYPES` (`packages/connectors/src/valuation-direction.ts`). The existing contract test then covers them.
- Priced and flagged rules arrive with the economic mapping in slice 2.

#### 2. Redline register (pure, deterministic)

New `packages/domain/src/redline/register.ts`. `buildRegister(rounds)` carries every change and comment forward between consecutive rounds of a chain.

**Change status when round N+1 arrives**
- **OPEN**: the same change is still tracked in N+1 (same kind, author, normalised text and paragraph anchor).
- **ACCEPTED**: N+1's accepted text reflects it (an insertion's text is present, or a deletion's text is gone from the matched paragraph).
- **REJECTED**: the opposite.
- **SUPERSEDED**: the other side made a new tracked change on the same anchor ("still contested in altered form").
- **NEEDS_REVIEW**: the anchor paragraph cannot be matched uniquely, so the match is flagged for a person rather than guessed.
- Changes in the latest round are OPEN.

**Comment status**
- OPEN or RESOLVED (the done flag) while present.
- **DELETED** when absent from the next round. It stays in the register, since a deletion is a negotiation signal.

**Version chain**
- Rounds are ordered, each with its side (BUYER/SELLER) and received date.
- The next turn is held by the side that did not send the latest round, since that date ("ball with the seller's counsel since 27 Oct"). It is computed from the chain, never typed.

#### 3. Storage, migration and RLS

Migration `2026112xxxxxxx_redline_rounds`, expand only (rollback: drop the table). New table `redline_rounds`:

| Column | Notes |
|---|---|
| `id`, `organization_id`, `deal_id` | |
| `document_id` | FK to documents; unique per deal |
| `chain` | Document title, e.g. "Purchase agreement" |
| `document_type` | LOI / TERM_SHEET / PURCHASE_AGREEMENT / DISCLOSURE_SCHEDULES / NDA / OTHER |
| `round` | int; unique per (deal, chain) |
| `sent_by` | BUYER / SELLER |
| `received_on` | date |
| `sync_run_id` | |
| `summary` | JSONB: counts, plus the unparsed list with locations |
| `parser_version`, `created_by`, `created_at` | |

**RLS**
- Reads require org and deal membership, plus `EXISTS (SELECT 1 FROM documents d WHERE d.id = document_id)`. Postgres applies the caller's documents policy to that subquery, so parsed data inherits the document's visibility: a seller sees rounds only on documents shared with them.
- Writes are buyer side only (`app_is_buyer_side`), with `created_by` set to the current user.
- Append-only: grant SELECT and INSERT only.

**Parsed records**
- They go through the existing engine, `executeSyncRun` in `packages/db/src/sync.ts`, with an `EvidenceSource` whose provider is `word_redline`.
- Connections follow the find-or-create pattern of `sourceUploads` connections in `packages/db/src/uploads.ts`: one per (deal, visibility), matching the document's visibility.
- Locator: the existing `provider_record` kind `{system:'word', site: documentId, resource: 'round-N/w:ins', id: revisionId}`. This adds no new locator kind.
- Quote: the change text.
- Each record cites the original document. The original bytes are never modified.

#### 4. API

New module `apps/api/src/redlines/`, modelled on `regulatory.module.ts` and its service.

- **`POST /v1/deals/:id/redlines/rounds`**: body `{documentId, chain, documentType, sentBy, receivedOn}`.
  - Reads the stored original through the same path as `DocumentsService.original` (hash re-check, audited).
  - Refuses anything that isn't .docx.
  - Parses the file, writes the round row and its sync run, and audits `redline.round.added`.
  - Round number = the chain's next. 422 with codes `NOT_DOCX`, `UNREADABLE_DOCX`, `ALREADY_A_ROUND`.
- **`GET /v1/deals/:id/redlines`**: chains with their rounds, the next-turn holder and since when, the register entries with status and citations, and the unparsed constructs.
- Contracts: `packages/contracts/src/redlines.ts`.
- Access: reads need document read access; writes need `DEAL_WRITE` and not a counterparty, the same as regulatory entries.

#### 5. Web

New page `apps/web/app/(app)/deals/[dealId]/redlines/page.tsx` and `actions.ts`, plus a "Redlines" entry in the Diligence tabs (`deal-tabs.tsx`).

**Per chain**
- The version chain: round, side, date and file.
- The line "Next turn: Seller's counsel, since …".
- The register table: kind, author, round, text, anchor, status badge, and a link to the document.

**Adding a round**

- The Documents page also gets a "Treat as a redline round" link for .docx rows.
