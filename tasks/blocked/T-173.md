Engine: claude

## Why

**Note (T-172):** T-172 moved the pilot surface only; the rest of the app's copy moves in T-172c, so "every key" means after T-172c. German for the pilot surface already exists, machine-made and unreviewed.


T-172 externalizes the app's strings; this task fills the ja, de and fr catalogs completely so the product ships in the target markets' languages (Kumar, 2026-11-26), with the deal vocabulary translated consistently — in diligence, a loose synonym for a term of art (escrow, indemnity, bridge) is a defect, not a style choice.

## Build

1. **Glossary first:** a per-language glossary of Pactlab and deal terms (pact, finding, valuation bridge, escrow, indemnity, holdback, claims register, the pack names and the six released pack families) recorded in docs and used as the translation source of truth; pack names follow the site's usage (T-171) where a site rendering exists.
2. **Full catalogs** for ja, de, fr covering every key from T-172, using the glossary; placeholders, plurals and ICU formatting preserved exactly (a contract test validates placeholder parity per key across locales).
3. **Layout pass:** screenshot sweep of the ten heaviest surfaces per locale; German string length and Japanese line-breaking fixed by catalog wording or layout tokens, never by shrinking fonts per locale.
4. **Native-review checklists** per locale in the PR, same pattern as the site (T-171): the locale is enabled for users when its checklist completes; until then it stays behind the pilot flag from T-172.

## Checks

- Placeholder-parity contract test; catalog completeness test (no missing keys); e2e smoke in each locale on the pact home.

## Acceptance

- A user set to ja, de or fr sees the entire app in that language with glossary-consistent terms.
- The three checklists are in the PR; enabling a locale is a config flip, not a deploy.
