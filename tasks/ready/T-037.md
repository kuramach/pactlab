# T-037 — Valuation direction: drag reprices, cushion confirms

Status: ready
Needs: none
Touches: packages/domain packages/calculations packages/connectors apps/api
Lane: valuation
Checks: pnpm lint && pnpm typecheck && pnpm test

## Brief

Product decision (2026-10-10, Kumar): every adapter/connector input must influence valuation in exactly one direction — drag (-1), cushion (+1), or neutral (0). Real-world asymmetry: clean diligence never raises the price; it confirms the thesis. Dirty diligence reprices the deal or hardens terms. There is no PRICE_INCREASE adjustment type — do not add one.

1. **Finding direction.** Add `direction: -1 | 0 | 1` to the finding domain model (`packages/domain/src/findings/types.ts`):
   - `-1` (drag): the finding MUST carry a `pricedRisk` (existing types only: PRICE_REDUCTION, REMEDIATION_COST, ESCROW, INDEMNITY) with $ range + basis. It feeds the seller-facing negotiation position through the existing purchase-price bridge. No new engine math.
   - `+1` (cushion): the finding carries a `valueConfirmation`: `{ valueDriver: string, impliedValue: { low: string, high: string, currency: string } | null, basis: string }`. Implied value is optional — "strong engineering culture" has none; "ARR is 8% above the CIM" does. Reported strictly as "value confirmed, not price paid".
   - `0` (neutral): informational; requires an explicit `rationale` string. Neutral is a decision, never the absence of data.
   - Direction is proposed by the signal/adapter default and confirmed or overridden by the human reviewer with rationale. AI/scanners propose; humans dispose (existing rule — only HUMAN moves a finding past DRAFT).

2. **Direction map registry.** New module in `packages/connectors` (e.g. `src/valuation-direction.ts`): `VALUATION_DIRECTION_MAP: Record<evidenceType, { findingDomain, defaultDirection, channel }>` covering every evidence type the connectors emit:
   - `code.repository_head` → CODE_PROVENANCE default -1 (ghost commits → REMEDIATION_COST/ESCROW), KEY_PERSON default -1 (concentration → ESCROW retention); healthy ownership/velocity signals default +1 (confirm team/continuity driver)
   - `delivery.issue`, `delivery.sprint` → OPERATIONS; velocity shortfall / high reopen rate -1 (growth haircut via assumption or priced term), strong delivery +1 (confirms execution driver)
   - `billing.invoice_line` → reconciled metrics below reported -1 (PRICE_REDUCTION), above reported +1 (confirms ARR driver — confidence, not a higher price), customer concentration -1 (ESCROW)
   - VDR-derived document findings → IP gaps / missing docs -1 (priced), clean title / confirmed owned IP +1 (cushion)
   - Add a contract test that enumerates every evidence type emitted by the adapters and fails the build if any is unmapped. Explicit 0 entries are allowed but must carry a rationale.

3. **Confirmed-value ledger.** Extend the asking-price comparison (`packages/calculations/src/valuation/asking.ts`) with a `confirmedValue` section: accepted +1 findings (finding id, label, value driver, implied value or null) plus totals. It MUST NOT flow into the bridge, enterprise value, equity price, or cash-at-close — report-only. The existing before/after-risks verdict logic is unchanged; cushion shows as coverage of the thesis, not dollars added.

4. **Buyer-confidential by default.** The cushion ledger is buyer-side (IC memo, walk-away confidence — never volunteered to the seller); the drag ledger generates seller-facing term proposals. Model this as a visibility flag on the ledger output and keep confirmed-value out of any seller-facing API response or export. Document the split in code comments.

5. **Backfill.** Existing findings proposed with `pricedRisk: null` (e.g. ghost-commit and key-person heuristics in `packages/domain/src/findings/code-signals.ts`) get an explicit direction under the new model: default -1 with a priced risk (REMEDIATION_COST for provenance, ESCROW for key-person), overridable to 0 with rationale at review. Confidence stays as review guidance — it does not scale money.

Validation: `validatePricedRisk` keeps requiring non-negative amounts with explicit currency and basis; add an equivalent validator for `valueConfirmation` (non-empty valueDriver and basis, ordered non-negative implied range when present).
