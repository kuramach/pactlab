# T-127 — Kafka demo pack: the real GitHub + Jira integration, recorded once and cached

Model: sonnet
Engine: claude
**Lane:** platform
**Context:** standard
**Touches:** packages/connectors (one-time recording, fixture replay data), apps/api (demo seed/ops, demo pool), apps/web (demo labelling), tests (connector contract, demo seed, e2e demo spec)
**Needs:** nothing — the live adapters (T-082), the Kafka pair harness, the cassette machinery and the demo pool all exist

## Why

Direction from Kumar (2026-11-16): demo accounts should be able to show how
Pactlab integrates with GitHub and Jira against a real, large public codebase —
apache/kafka on GitHub plus the KAFKA project on Apache Jira, the pair T-074
verified end to end. Today the demos carry only synthetic fixture data
(Brightwave and the other invented companies), so a prospect never sees a real
integration. Kumar's decision on freshness: **pull once, cache always** — the
demo never makes a live call.

## What to build

1. **One-time recording.** With the existing live adapters and the kafka-pair
   harness (`packages/connectors/src/live/`), pull a bounded, representative
   slice of the real pair: recent merged PRs with their reviews and check
   runs, commits whose messages carry KAFKA- keys, and the Jira issues those
   keys resolve to. Bound it deliberately (a fixed window/count, chosen so
   the snapshot stays reviewable and the demo loads fast) and record the pull
   date in the snapshot.
2. **Permanent cache.** Store the recording as fixture-shaped data the
   existing fixture adapters (`github/fixture.adapter.ts`,
   `jira/fixture.adapter.ts`) can replay, so the evidence landing in the demo
   pact is exactly the shape a live pull produces — same evidence types
   (already registered in VALUATION_DIRECTION_MAP), same cross-link
   extraction. The cache is committed once and never refreshed by any job:
   the demo-refresh machinery (T-124) must not re-pull, overwrite or age it
   out.
3. **Demo case.** Add a demo pact to the demo pool/seed alongside the
   synthetic companies, presented as engineering diligence on a real
   open-source target; its code and delivery sources are the cached Kafka
   snapshot. Label it honestly wherever a viewer sees it: real apache/kafka
   data, recorded once on the pull date — not a live connection, not
   synthetic.
4. **No network at demo time.** Seeding or opening this demo performs zero
   live calls (no GitHub or Jira requests, token or anonymous).

## Checks

- Connector contract tests still pass; the replayed snapshot yields
  cross-links (KAFKA- keys, both directions) in the demo pact's evidence.
- Demo seed test: the Kafka case seeds from cache with the live adapters
  disabled/unreachable.
- E2E: a demo spec in the style of `apps/e2e/specs/demo-engineering.spec.ts`
  loads the Kafka demo and shows its GitHub/Jira evidence.
- A guard that the demo refresh/sweep leaves the Kafka snapshot untouched.

## Out of scope

- No live-connection demo mode (deliberate: rate limits, data drift —
  Kumar's call, 2026-11-16).
- No changes to live adapter behaviour; this task consumes them as they are.
- No new evidence types.
