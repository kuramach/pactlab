# T-136 — In-workflow document signing: DocuSign embedded signing
Engine: claude
Model: opus

**Lane:** platform
**Context:** deep
**Touches:** documents/LOI flow (T-119), pact state machine, notifications/webhooks, env/secret config, spec
**Needs:** a DocuSign developer/demo account for dev environments (Kumar creates it when the loop reaches that step; production DocuSign account is a later, separate go). Builds on T-119 (LOI generation + DocuSign path), which is merged.

## Origin

Kumar's question (2026-11-16): how do signatures happen for documents in the Pactlab workflow — the ideal is that parties sign without leaving the workflow. Recommendation accepted and filing approved 2026-11-17: integrate DocuSign embedded signing (best-in-class; do not build signing) — consistent with T-119's DocuSign direction.

## Build

1. **Envelope creation from Pactlab documents.** First surface: the T-119 LOI (generated from agreed terms, drafts private until sent — that rule is unchanged). The design must generalize to other pact documents (approved terms documents, IC-approved packages) without rework: a document -> envelope service, not an LOI-only hack.
2. **Embedded signing for counterparties.** Sellers/counterparties sign inside an embedded DocuSign session launched from Pactlab — no Pactlab account required, consistent with the guest model (sellers are passwordless; identity for signing is the email invitation + DocuSign's embedded-session flow). The buyer-side user sends and tracks from within the pact.
3. **Status as pact state.** Envelope status (sent / delivered / signed / declined / expired / voided) is pact state, driven by DocuSign Connect webhooks (idempotent handlers; polling fallback for a missed webhook, never the primary path). Status changes land in the pact timeline.
4. **Signed artifact as evidence.** On completion, the signed document and the DocuSign Certificate of Completion are stored in the pact as evidence — the signed file preserved byte-for-byte as the legal artifact (the same principle as T-089's original-file rule). Declines and expiries are recorded with reason where DocuSign provides one.
5. **T-119 wiring.** LOI exclusivity expiry tracking (already in T-119) reads the real signing state: an LOI envelope expiring unsigned surfaces against the exclusivity clock, not as a silent dead end (T-125 no-silent-failures rule).
6. **Config.** DocuSign credentials (integration key, account, environment: demo vs production) live in env/secret config per environment, like the existing provider settings. No envelope is ever sent from a non-live environment to a real counterparty address — demo envelopes go to demo/test recipients only.

## Acceptance

- End to end on the demo account: an LOI generated in a pact is sent for signature from within Pactlab; a guest signer completes it in an embedded session; status transitions appear in the pact timeline via webhook; the signed PDF + certificate are stored as pact evidence, byte-for-byte.
- Webhook idempotency proven by test (duplicate delivery changes nothing twice).
- A declined and an expired envelope each land in the pact record with their status visible — no silent states.
- Tests run against the DocuSign demo/sandbox environment or recorded fixtures; CI never sends a real envelope (CLAUDE.md: CI never calls live third parties for gating tests).
