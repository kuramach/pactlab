# T-150 — Live log triage in prod: CloudWatch errors to Bedrock verdicts, email and GitHub review, approved issues become tasks

Engine: claude
Model: opus
Lane: platform
Context: deep
Touches: infra/cdk docs .github/workflows scripts
Needs: none

## Why

Today, errors in live are found only when someone goes looking, or when a user hits one. Kumar's direction (2026-11-22): detection and triage must run in prod itself and must never depend on the Mac mini — it is a dev machine and may be off. Review reaches Kumar where he already works (email and GitHub), and approved findings enter the normal task queue. AWS-native, pay-as-you-go pieces only, all already available in the live account: CloudWatch Logs Insights, Lambda, EventBridge, Bedrock (restored and verified 2026-11-20), SES (production access approved 2026-11-18, 50,000/day).

## Build

1. **Log inventory and retention.** Identify the live (prod) CloudWatch log groups for the api, worker and web ECS services (us-east-2) and make sure CDK sets retention of at least 30 days on them. The sweep window is "since the last successful run" (a stored watermark); the first run covers the previous 24 hours.
2. **Scheduled sweep.** An EventBridge daily schedule invokes a Lambda in the live account (CDK-deployed; handler source lives under infra/cdk). The Lambda runs Logs Insights queries for error-level entries, unhandled exceptions, 5xx responses and failed worker jobs, then clusters results by error signature (normalized message plus top stack frame or error code) with occurrence counts and first/last seen per cluster.
3. **Triage state.** A small CDK-managed store (DynamoDB table or S3 object, builder's choice) records per signature: first seen, last seen, last reported count, status. A cluster is reportable when it is new, or when its count since the last report passes a documented threshold (sane defaults, e.g. doubles or +50 occurrences). State also holds the sweep watermark.
4. **Bedrock triage.** For each reportable cluster (cap per run, default top 20 by count), one Bedrock Converse call (the account's default Claude alias) receives the signature, counts, first-seen, recent live deploy timestamps (from ECS service/deployment data, so "started right after deploy X" can be stated), and a few scrubbed sample lines. It returns a structured verdict — likely_bug, likely_noise or needs_human_eyes — a one-paragraph plain-English summary, and a one-line fix sketch for likely bugs.
5. **Email digest.** If anything is reportable, send ONE digest via SES from the live account to kumar@pactlab.ai (recipient set by config, not hard-coded in the handler). Ranked: new clusters first, then by count. Each entry: summary, count, first seen, verdict, fix sketch, link to its GitHub issue. Noise-classified clusters appear in a short "classified as noise" section so Kumar can audit the classifier. Nothing reportable means no email — silence is healthy.
6. **GitHub issues.** For each likely_bug and needs_human_eyes cluster, open ONE issue in kuramach/pactlab titled "[live-triage] <summary>", labelled live-triage, body carrying the cluster detail: counts, first/last seen, scrubbed samples, verdict, fix sketch, and the Insights query text for reproduction. Dedupe by a signature marker in the issue body: if an open live-triage issue already carries the signature, add a comment with the new counts instead of opening a duplicate. Credential: a fine-grained GitHub token scoped to this repo with Issues write ONLY, held in Secrets Manager (pactlab/live/github-triage) and injected into the Lambda by CDK secret reference. Include a scripts/ helper in the ai-key.sh / signing-key.sh pattern for Kumar to load the token value; the value never transits the repo.
7. **Approval becomes a task.** A GitHub Actions workflow (.github/workflows/triage-to-task.yml) fires when a live-triage issue receives the triage-approved label. It computes the next free T-number from the repo, writes a house-format task file into tasks/ready/ (title from the issue; body carries the cluster detail and a link back to the issue), commits it to main, comments on the issue with the task ID, and applies a task-filed label. The workflow uses the repo's own GITHUB_TOKEN, never the Lambda's token. Closing an issue as noise needs no workflow. If a label trigger proves awkward, an issue-comment trigger is acceptable — builder's judgment, documented in the runbook.
8. **Docs.** docs/runbooks/log-triage.md: how it works, thresholds, how to pause the schedule, how to rotate the GitHub token, cost shape. An ADR recording the prod-native decision and the Mac-independence rationale (Kumar, 2026-11-22).

## Kumar prerequisites (do not block the build; they gate activation)

- Create the fine-grained GitHub token (repo kuramach/pactlab, Issues read/write only) and load it with the helper script from step 6 — gates the first real issue creation.
- Approve the dry-run digest (see Checks) before live email and issue creation are switched on.

## Guardrails

- The Lambda's role is read-only on logs (StartQuery / GetQueryResults / DescribeLogGroups on the live groups only), Bedrock invoke on the triage model only, SES send to the configured recipient only, and read/write on its own triage state store. No write access to any application resource.
- Scrub before anything leaves AWS: samples capped at a few lines and truncated; strip emails (other than the operator's), tokens, authorization headers and long hex/base64 runs. Never include request bodies in an email or an issue.
- No task file is ever created without Kumar's triage-approved label, and this system never opens fix PRs. Filed tasks go through the loop's normal gates.
- Pay-as-you-go only: queries scoped to the watermark window; Bedrock calls capped per run. No standing compute beyond the scheduled Lambda.
- Every component runs in AWS or GitHub. The Mac loop enters only when a filed task is later built; if the Mac is off, approved tasks simply wait in tasks/ready/.

## Checks

- Unit tests: signature normalization and clustering, sample scrubbing, reportability thresholds, issue dedupe marker, watermark handling, and the workflow's task-file rendering including next-T-number computation.
- CDK synth/snapshot tests for the new resources and the Lambda role's permissions.
- A dry-run mode (env flag): runs the queries and the Bedrock triage against live logs and writes the would-be digest and issue bodies to the Lambda log instead of sending or opening anything. Note: dev's Bedrock access is not enabled yet, so the acceptance dry-run happens against live in dry-run mode.

## Acceptance

- Dry-run against live produces a correct digest draft (clusters, counts, verdicts) from real log data, reviewed by Kumar.
- After Kumar loads the GitHub token and gives the go: one real run sends exactly one digest email and opens deduped GitHub issues for the likely bugs.
- Labelling an issue triage-approved produces a valid task file in tasks/ready/ via the workflow, and the issue is commented with the task ID.
- Runbook and ADR merged; thresholds and the pause procedure documented.
