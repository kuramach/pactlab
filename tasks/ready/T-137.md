# T-137 — Diagnose the nightly integration-live failures
Engine: claude
Model: sonnet

Lane: platform
Context: standard
Touches: packages/connectors docs
Needs: none
**Needs note:** nothing to start — this task runs on the Mac, where the suite can be run directly and Actions logs read locally. Scope is the integration-live suite only; the unit suite is T-134.

## Symptom (verified through 2026-11-17)

The nightly `integration-live` workflow has been red on every recent run (through run #22, 2026-11-17). The suite exercises the real GitHub + Jira adapters (T-074/T-082) against apache/kafka and the KAFKA project on Apache Jira, and it ran green on demand via `pnpm test:live` on 2026-10-25. Something has drifted since: adapter, upstream services, credentials, or the suite itself. Nobody has yet seen the actual failure output (the agent's GitHub connector cannot download job logs; on the Mac both the suite and the logs are directly reachable).

## Job

1. Run the suite locally exactly as CI runs it; capture the real failure output — which adapter, which call, which assertion or error.
2. Classify the root cause into one of: adapter bug (ours), upstream drift (GitHub/Jira API or the Kafka project's data changed shape), rate limiting (anonymous GitHub access is 60 req/hr vs 5,000 authenticated — check which the CI run uses), credential/secret problem in the workflow environment, or suite defect (over-specific assertions on live data).
3. Fix what is ours at the root. For rate limiting, the fix is authenticated access in CI via the workflow's existing token mechanisms — the connections' read-only posture (Kumar, 2026-10-25) is not weakened: read scopes only, payloads never logged.
4. For upstream drift, make the assertions assert the adapter contract (shape, cross-links, required fields) rather than the upstream project's current data — live-data suites must tolerate the data changing.
5. If the blocker is genuinely external and cannot be fixed from here, the deliverable is the precise diagnosis: the failing call, the response, and the specific external change needed — stated in the PR, not a shrug.

## Acceptance

- The failure output is quoted in the PR with the classification and root cause.
- integration-live is green on its next nightly run after the fix — or the PR names the exact external blocker with evidence.
- No retry-until-green loops, no widened timeouts as the "fix," and no assertion simply deleted: every changed assertion is justified by the contract-vs-data distinction above.
