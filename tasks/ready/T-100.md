# T-100 — Release version tags: one human number per release
Engine: claude
Model: sonnet

**Lane:** infra
**Context:** standard
**Touches:** .github/workflows (new release.yml; deploy.yml summary line only), scripts/next-release-tag.sh (new), docs/release.md (new)
**Needs:** none. Builds on the ADR 0019 deploy model already live in deploy.yml.

## Kumar's ask (2026-11-05)

Kumar asked how releases work across the four environments (dev, qa, stage, live) and whether there is a release number. Answer today: no — no git tags, no GitHub Releases; a release is identified only by its commit SHA, which is also the image tag. He asked for "a simple scheme to add a version tag."

## Progress (2026-11-05)

Built, as written, plus Kumar's addition: **the running version shown in the app**.
- **Where it shows:** the app footer, Settings → About Pactlab, `/health` (`version`, `sha`) and bug reports.
- **How it gets there:** each deploy writes `/pactlab/<env>/release`, never the task definitions, so a new version alone rolls no service.

## The scheme

**CalVer: `vYYYY.MM.N`** — year, month, and a per-month sequence starting at 1. First release in November 2026 is `v2026.11.1`, the next one that month `v2026.11.2`, December starts again at `v2026.12.1`. No major/minor semantics to invent or maintain pre-launch; the number always increases and sorts correctly.

1. **Cutting a release is one deliberate dispatch.** New workflow `release.yml` (`workflow_dispatch`, main only): computes the next tag, creates an annotated git tag on the dispatched commit, and creates a GitHub Release for it with auto-generated notes. It refuses to run off main and refuses a tag that already exists. Nothing auto-tags on merge — a release is an act, not an accident.
2. **Next-tag computation is a small pure script** — `scripts/next-release-tag.sh`: given the existing tag list and a target `YYYY.MM`, it prints the next `vYYYY.MM.N`. Kept separate from the workflow YAML so it is testable on its own.
3. **Deploys do not change.** deploy.yml keeps dispatching from main exactly as ADR 0019 specifies, and container images keep their commit-SHA tags. Do NOT dispatch deploys from a tag ref: the branch guard rejects non-main refs for qa (and live, later), because `github.ref_name` would be the tag name. Instead, deploy.yml resolves the version for the commit it is deploying (a tag pointing at `github.sha`) and prints one line in the run summary — `Release v2026.11.1 (sha 9f361042)` — or just the SHA when the commit carries no tag, exactly as today.
4. **Runbook** — `docs/release.md`: how to cut a release (dispatch, tag, then promote main dev → live — the interim path per T-101, which supersedes the ADR 0019 four-step promotion until the packs are complete), how to answer "which release is on stage?" (the deploy run summary line, or the tag pointing at the SHA the stack reports), and rollback as it honestly works today: re-dispatch deploy on main, or revert and re-dispatch. Link ADR 0019 rather than restating it.

## Non-goals

- No semver, no package.json version fields, no hand-written changelog (GitHub's generated release notes suffice).
- No change to image tagging, promotion order, branch guards, or the GitHub Environment approvals.
- Live is not added to the deploy dispatch options here; that is separate work.

## Checks

- `next-release-tag.sh` behaves: no tags for the month → `.1`; `.1` and `.3` present → `.4` (max + 1, gaps ignored); tags from other months ignored.
- A `release.yml` dispatch on main creates the tag and the GitHub Release; a second dispatch creates the next sequence number; a dispatch from a non-main ref fails.
- A deploy of a tagged commit shows the `Release v… (sha …)` line in its run summary; a deploy of an untagged commit behaves exactly as before.
- `docs/release.md` is merged and consistent with ADR 0019.
