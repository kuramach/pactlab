## Bugs: Hosting cost

### Pagination
1. **Metered tables silently cut at 100 rows:** By organization, By pact, By person and By model show `slice(0, 100)`, with no "showing 100 of N" and no way to see the rest. `apps/web/app/admin/hosting-cost.tsx`, `MeteredTable`.
2. **No pagination anywhere else:** By AWS product, By environment, By month and Rates render every row. By AWS product can run to dozens of services.
3. **The API returns every row of every breakdown in one response** (`GET /v1/admin/cost`), so the payload grows with organizations, pacts and people. There is no `limit`, cursor, `sort` or per-section request.
4. **No sorting or search:** you can't reorder by AI or by storage, or find one organization, pact or person.

### Speed
5. **Every page view recomputes everything:** `app_ops_cost_ai_usage` scans `ai_runs` for the whole period, and `app_ops_cost_storage_usage` scans every document. The five breakdowns are rebuilt in Node on each request, even for sections nobody scrolls to.
6. **`ai_runs` has no index that serves this query:** the existing index is `(organization_id, deal_id, created_at)`, and the cost query filters on `created_at` alone across all organizations.
7. **Too many rows come back to Node:** AI usage is grouped by day × model × organization × pact × person in SQL, then rolled up again in TypeScript. That is far more rows than the views need. The day grouping exists only to apply the rate in force on each day.
8. **The page blocks on all sections at once:** it is one server render behind one API call, with no per-section streaming or lazy loading.
9. **Cost Explorer lines are re-read and re-aggregated per request** for month, environment and service, with no cached rollups.

## Bugs: the rest of the admin console

10. **Users silently stops at 200:** `app_ops_users` ends in `LIMIT 200`, so with 1,000 users, 800 never show and nothing says so. There is no pagination, no "of N", and sorting is fixed (organization, then name). Search exists (`q`, organization filter) but returns at most 200 rows.
11. **Organizations has no limit and no pagination,** and it is slow per row: `app_ops_organizations` runs correlated subqueries for each organization (owners, member count, three deal counts, and `sum(input_tokens)` / `sum(output_tokens)` over all of `ai_runs`). It renders every organization in one table.
12. **The audit log is capped at 200 rows** (at most 500), newest first, with no pagination to reach older events beyond the action filter.
13. **The bug inbox, connections and promo codes** render every row in one table, with no pagination.
14. **Every tab is one server render behind one call,** with no per-table loading.

## Likely fixes (to confirm when this is picked up)
- **One shared pagination contract:** in `packages/contracts`, a `{ items, nextCursor, total? }` response and `?cursor=&limit=` query, keyset on `(created_at, id)` or a stable sort key, with `limit` capped at 100. The API, the web and MCP all use it, and MCP tools pass `cursor` through.
- **No silent caps:** a hard `LIMIT` without "has more" becomes a page (bugs #10, #12, #16 and #28).
- **Web:** one table footer component in `@pactlab/ui` ("showing X–Y of N", next and previous, the page in the URL) used by every list above. Search and sort are server-side where a list can pass a few hundred rows (deals, documents, findings, members, people).
- **One pagination pattern for the whole console:** server-side keyset pagination in each `app_ops_*` function (`p_after`, `p_limit`, a returned total or "has more"), and the same table footer everywhere ("showing X–Y of N", next and previous), with the page in the URL. Users and Organizations come first.
- **Organizations without per-row scans:** aggregate counts and tokens in one grouped query or a rollup, not correlated subqueries.
- **Pagination:** server-side, per breakdown (`section`, `limit`, `cursor` or `offset`, and `sort`), with "showing X–Y of N" and next/previous controls on each table. Rates get pagination too.
- **Per-section requests,** so the page renders the summary first and each table loads on its own (Suspense or streaming).
- **A daily usage rollup:** a table such as `cost_usage_daily` (day, organization, pact, person, model, runs, tokens, byte-days), filled incrementally (today's rows on view, past days once). Breakdowns then read the rollup.
- **An index** on `ai_runs (created_at)`, or a partial or covering index, if the rollup doesn't replace the scan.
- **Push the aggregation into SQL** per breakdown, with rates joined by date in SQL, so Node gets the final rows.
- **A spend rollup:** precompute month, environment and service totals at each Cost Explorer refresh.
