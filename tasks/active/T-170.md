# T-170 — Multi-currency foundation: USD, GBP, EUR, JPY and INR done properly end to end

Engine: claude
Model: opus
Lane: core
Context: deep
Touches: packages/contracts packages/domain packages/calculations packages/db apps/api apps/web packages/ui docs
Needs: none
Checks: pnpm lint && pnpm typecheck && pnpm test && pnpm test:integration && pnpm test:fixtures && pnpm test:e2e

## Why

Kumar's target markets (2026-11-26): US, UK, Germany, France, Japan and India. Deals in those markets are priced in GBP, EUR, JPY and INR, not only USD. The pact contract already carries `baseCurrency` (ISO code, default USD) — this task makes currency real and safe across the whole money path before any localization lands (T-171 onwards). Money correctness rules: a pact's amounts live in its own currency; nothing is ever converted silently.

## Build

1. **Coverage audit and completion.** Trace every amount-bearing surface — findings, valuation bridge, terms, financing, imports, QoE, reports, billing display — and confirm each amount is interpreted in the owning pact's `baseCurrency`. Fix any surface that assumes USD. Launch currency set, fully formatted and tested: USD, GBP, EUR, JPY, INR (the ISO schema stays open to other codes; the launch set is what we test).
2. **Minor units and rounding.** Per-currency minor units from the ISO table (JPY has zero decimals — the classic bug); storage, calculation rounding (packages/calculations) and display all honour them. Contract tests: a JPY bridge with whole-yen amounts, an INR bridge, a EUR bridge, each recomputed exactly.
3. **One formatter.** A single money/number/date formatting entry point (Intl-based, locale + currency aware) in the shared packages, used by web, site, emails and generated documents; the scattered hardcoded Intl calls in apps/web are migrated to it. en-IN grouping (lakh/crore) comes from Intl, never hand-rolled.
4. **Imports.** A P&L or data import declares its currency; a mismatch with the pact's currency is flagged to the reviewer (ask-when-unsure pattern) and the import cannot silently mix currencies inside one statement set. Multi-year trend reads (the pack requirement) compare like with like — same currency across years, or the trend finding states the break.
5. **Aggregation and FX.** Cross-pact totals (home summary, portfolio views) group by currency and never sum across currencies. If a view offers a converted figure, it is labelled with the rate and its date, from a recorded FX source configured per deployment — display only; the pact's own numbers never change. No conversion inside the valuation bridge, ever.
6. **Docs.** An ADR recording the money rules (pact currency is canonical, no silent conversion, labelled display conversion only) and a runbook note on adding a currency.

## Checks

- The per-currency contract tests in step 2, plus the existing money suites unchanged and green.
- Formatter unit tests: USD/GBP/EUR/JPY/INR rendering in en-US, en-GB, de-DE, fr-FR, ja-JP, en-IN locales, including zero-decimal and lakh grouping cases.
- Import tests: currency mismatch flagged; mixed-currency statement set refused with a clear reviewer message.

## Acceptance

- A demo pact in EUR and one in JPY run end to end (import → findings → bridge → terms → report) with every figure correctly denominated and formatted.
- No surface in the app renders a bare `$` for a non-USD pact.
- ADR merged; the formatter is the only Intl entry point for money in the web app.
